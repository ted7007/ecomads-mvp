# Рекомендации первого спринта

Реализован диагностический срез № 3 и № 6. Уточнения пользователя от 12 октября 2026 года имеют приоритет над фиксированным окном исходного ТЗ:

- Пользователь передаёт начало и конец периода; расходы, единицы, средняя сумма на единицу, пороги и ДРР считаются за этот же период.
- № 3 не ждёт 30 кликов. Условие: Q = 0, S ≥ max(2 × P × N; 300 ₽).
- Для всех подключённых кабинетов доступны предварительные карточки при полной загрузке; данные могут уточняться. Точных ставок и исключений в этом выпуске нет.

## Поведение

№ 6 требует Q ≥ 3, Dmin > N и D̂_plus > N при добавлении одной заказанной единицы. Денежные сравнения используют decimal без округления. N и ДРР в движке — доли; табличные строки возвращают проценты.

Норма выбирается в порядке товар в кампании → кампания → кабинет → 20%. Существующие сохранённые нормы, включая 30%, остаются явными значениями. Пустая норма товара возвращает наследование; изменения имеют версии и журнал ревизий.

Полнота fullstats проверяется по всем дням. Полнота кластеров — по объединению успешно загруженных интервалов для точной пары кампания/артикул. Неполная загрузка, неизвестный Q и отсутствие средней цены не превращаются в ноль. Если товар отсутствует в fullstats за день с положительным расходом кампании, его покрытие считается неподтверждённым.

Старые товарные строки имеют `recommendation_fields_verified = null`; они требуют повторного успешного импорта. Импортер отклоняет ответ без обязательных числовых полей, сохраняет неизвестный shks отдельно и добавляет наблюдение O/Q/R после каждой успешной загрузки всех подключённых кабинетов. Возраст дня не объявляется доказанной зрелостью: `unverified`, для текущего дня — `open_day`.

В одном ответе API находятся карточки и табличные агрегаты их расчёта. При смене периода React запрашивает новый результат. Ошибка запроса отображается как ошибка; прежний период не выдаётся за новый.

Каждый завершённый расчёт сохраняется неизменно. Fingerprint учитывает факты, покрытие, настройки правил, нормы и окно. Повтор одинакового запроса использует прежний runId; изменение данных или нормы создаёт новую версию. Параллельные запросы не создают дубли. Существующие пользовательские решения legacy-карточек в новые расчёты не переносятся.

## Доступность в сервисе

По решению пользователя от 13 октября 2026 года ограничения пилота и список разрешённых кабинетов удалены. Новые рекомендации включены по умолчанию и отображаются на странице кампании любого подключённого кабинета. Выбирать кабинет, указывать его GUID или отдельно включать пилот не требуется.

Проверки владельца, полноты загрузки и обязательных полей сохраняются. Карточки помечаются «Предварительно», а экономика кластера — «Оценка». Настройка `SourcesComparable` по умолчанию true означает использование описанной оценочной модели по контрактам fullstats/normquery, а не доказательство одинаковой атрибуции или равенства итогов. При выявленной несовместимости источников администратор может отключить экономические правила этой настройкой.

Остаётся только общий технический выключатель `Wb__Recommendations__Enabled=false` для отключения модуля целиком; список кабинетов не поддерживается.

При обновлении приложения EF применяет миграцию `AddRecommendationFoundation`. Для старых строк нужен обычный повторный импорт fullstats выбранного периода; заполнение только отсутствующих дней не подтверждает уже существующие строки. Если данные ещё не готовы, сервис показывает соответствующую причину.

На экране кампании выбранный период управляет расчётом. Норму товара можно изменить в блоке «Нормы ДРР по товарам этой кампании». Для неполного периода используется существующий интерфейс загрузки WB.

## API

```text
GET /api/wb/campaigns/{campaignId}/recommendations?startDate=2026-10-01&endDate=2026-10-07
GET /api/wb/campaigns/{campaignId}/recommendations/runs/{runId}
GET /api/wb/norms/campaigns/{campaignId}/articles
PUT /api/wb/norms/campaigns/{campaignId}/articles/{articleId}
    { "targetDrr": 20 }
    { "targetDrr": null } — вернуть наследование
```

Период обязателен: 1–366 дней включительно, даты по МСК. Запросы используют БД и не обращаются к WB. Доступ к расчёту, его снимку и норме товара проверяется по владельцу кабинета и привязке товара к кампании.

Ответ содержит `enabled`, `runId`, `schemaVersion`, `window`, `calculatedAtUtc`, `cards`, `evaluations`, `rows` и `coverage`. У оценки есть subject, facts, norm, quality, economy и независимые результаты двух правил. Норма и экономика в этом контракте — доли; `rows.estimatedDrr` — проценты для совместимости с таблицей.

У каждого правила ID/версия, enabled, status, reasonCode, threshold, explanation, actionKind и free/pro. Текущий actionKind — `review`, tier — `free`. При отсутствии данных зависимое правило skipped; выключенное — disabled. Доля evaluated считается по включённым проверкам.

## Фоновый проход

Фоновый расчёт использует тот же движок, но самостоятельное окно 14 дней D−15 … D−2 относительно ночного слота 06:15 по МСК. Он не заменяет пользовательский период. Двухминутный проход повторно использует неизменившийся run, а при изменении входов создаёт новую версию.

При разрешённом автоматическом обновлении существующая очередь постепенно догружает отсутствующие семидневные интервалы кластеров. Загрузка fullstats и повторное чтение последних семи дней используют существующее расписание. Автоматические запросы не выполняются для заблокированного/просроченного токена или отключённого обновления кабинета. Часть истории отражается в качестве результатов.

Журнал расчётов и наблюдения статистики очищаются по настраиваемому сроку `RetentionDays` (90 дней по умолчанию). Это технический журнал; политику будущих пользовательских решений и измерений нужно определить отдельно в спринте 5.

## Проверка источников

Без новых запросов WB проверены локальные `.env.wb-fullstats-response.json` и `.env.wb-normquery-response.json`: 559 листовых товарных строк fullstats, во всех есть shks и sum_price; 7 235 кластерных строк, во всех есть shks. Сырые данные и токены в отчёт не включены.

Предыдущая проверка агрегатов описана в `docs/cluster-order-estimates.md`: совпадение единиц по 64 из 84 общих разрезов и различие по 20. Это подтверждает структуру и необходимость раздельной оценки, но не доказывает одинаковую атрибуцию. Экономика кластера остаётся моделью со сценарным отклонением цены, не фактической выручкой.

## Проверки и следующие спринты

Итог проверки 13 октября 2026 года после удаления ограничений пилота: полный набор **90/90 тестов** прошёл на временном PostgreSQL, включая доступность для двух разных продавцов без выбора кабинетов. Frontend ранее собран (`tsc` и Vite); EF не обнаружил изменений модели без миграции. Новые компоненты визуально проверены на широком и узком экранах с синтетическими данными. Результат последнего полного прогона сохранён в `artifacts/recommendation-tests/recommendations-general-availability.trx`.

Проверяются денежные границы, малые/отсутствующие клики, Q вместо O, строгие сравнения, добавление единицы, округление, неизвестные поля, объединение интервалов, наследование/сброс норм, повторные/параллельные запросы, смена периода, неизменность снимка и изоляция продавцов. Интеграции выполняются на временном PostgreSQL через Testcontainers; рабочая БД не используется.

```text
dotnet test Ecomads.WebApplication.Tests/Ecomads.WebApplication.Tests.csproj --no-restore
cd Ecomads.WebApplication/ClientApp
npm run build
```

Готовая основа следующих спринтов: чистый движок, независимые RuleEvaluation, версионируемая норма, окна и источники, неизменные runId/evaluationId. Дополнительно потребуются политики действий/конфликтов, запуск/цели, оперативные снимки, LLM и отдельный жизненный цикл. Наличие runId не означает, что действие продавца выполнено или экономия доказана.
