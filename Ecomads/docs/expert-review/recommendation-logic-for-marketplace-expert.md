# Логика формирования рекомендаций EcomAds для экспертной оценки

Документ описывает текущую фактическую логику backend-рекомендаций EcomAds. Его цель — дать эксперту по маркетплейсам понятную базу для проверки правил: какие ключевые слова система считает проблемными, какие считает перспективными, какие действия предлагает и где нужны правки.

## Короткий вывод

Система формирует рекомендации не напрямую через LLM. Backend сначала рассчитывает метрики, классифицирует ключевые слова по правилам, назначает разрешённые и запрещённые действия, считает приоритет, а LLM только превращает уже готовые backend-insights в читаемый текст.

Главная бизнес-логика сейчас строится вокруг:

- целевого ДРР;
- расхода;
- заказов;
- кликов;
- выручки / заказанной суммы;
- уверенности в данных.

Текущий MVP не учитывает маржинальность, остатки, категорию товара, сезонность, стратегию ставок, позицию в выдаче и семантическую релевантность запроса как полноценные факторы принятия решения.

## Источник данных

Для кампании берутся:

- последняя загруженная общая статистика кампании;
- статистика по ключевым словам за тот же период, если она есть;
- если статистики ключей за этот период нет, берутся все ключевые слова кампании.

Для каждого ключевого слова используются поля:

- фраза;
- показы;
- клики;
- расход;
- заказы;
- выручка / заказанная сумма;
- CTR;
- ДРР;
- период статистики.

## Основные настройки MVP

Текущие пороги:

```text
Целевой ДРР = 30%
Минимум кликов для вывода = 30
Минимум расхода для вывода = 500 ₽
Минимум заказов для позитивного вывода = 3
Максимум insights для LLM = 20
```

Дополнительные коэффициенты:

```text
Оценка экономии при плохом ДРР = 30% от расхода
Оценка масштабирования = +20% к расходу при сохранении текущего ДРР
```

## Расчёт метрик

Backend пересчитывает метрики сам:

```text
ДРР = Расход / Выручка * 100
CTR = Клики / Показы * 100
CPC = Расход / Клики
CR = Заказы / Клики * 100
CPO = Расход / Заказы
Средний чек = Выручка / Заказы
Средние заказы в день = Заказы / Количество дней периода
```

Правила для пустых значений:

- если выручка равна 0, ДРР не рассчитывается;
- если показы равны 0, CTR не рассчитывается;
- если клики равны 0, CPC и CR не рассчитываются;
- если заказы равны 0, CPO и средний чек не рассчитываются.

## Уровень уверенности

Система присваивает каждому ключевому слову уровень уверенности.

### High

```text
Клики >= 100
или Расход >= 3000 ₽
или Заказы >= 10
```

### Medium

```text
Клики >= 30
или Расход >= 500 ₽
или Заказы >= 3
```

### Low

```text
Все показатели ниже Medium
```

Уверенность влияет на приоритет и на запрет агрессивных действий. Если уверенность низкая, система запрещает резкие решения: немедленное минусование, агрессивную смену ставки и масштабирование.

## Типы рекомендаций по ключевым словам

Ниже описаны правила, по которым ключевое слово попадает в определённый статус.

Порядок проверок важен:

```text
1. LowData
2. BadSpendWithoutOrders
3. ScaleCandidate
4. WatchCandidate
5. BadDrr
```

Если правило сработало, следующие правила для этого ключа уже не проверяются.

## LowData — мало данных

Ключ получает статус `Мало данных`, если одновременно:

```text
Клики < 30
и Расход < 500 ₽
и Заказы < 3
```

Смысл:

```text
По ключу пока нельзя делать жёсткий вывод.
```

Разрешённые действия:

- собрать больше данных;
- наблюдать.

Запрещённые действия:

- минусовать ключ;
- масштабировать;
- агрессивно менять ставку;
- немедленно минусовать.

Вопрос эксперту:

- достаточно ли этих порогов для разных ниш, или нужно разделять правила по цене товара / категории / среднему чеку?

## BadSpendWithoutOrders — расход без заказов

Ключ получает статус `К удалению`, если:

```text
Расход >= 500 ₽
и Заказы = 0
и Клики >= 30
```

Смысл:

```text
Ключ уже потратил значимый бюджет, но не принёс заказов.
```

Разрешённые действия:

- снизить ставку;
- рассмотреть минус-слово;
- перенести в наблюдение.

Запрещённые действия:

- повышать ставку;
- масштабировать.

Ожидаемый эффект:

```text
Потенциальная экономия = весь расход по ключу за аналогичный период.
```

Вопрос эксперту:

- корректно ли считать 500 ₽ и 30 кликов достаточным основанием для рекомендации к исключению/снижению ставки?
- нужно ли учитывать цену товара, средний чек, маржу и длину цикла покупки?

## ScaleCandidate — кандидат на масштабирование

Ключ получает статус `Эффективное`, если:

```text
Заказы >= 3
и ДРР рассчитан
и ДРР <= 30%
и уверенность не Low
```

Смысл:

```text
Ключ приносит заказы с приемлемой экономикой и может быть точкой роста.
```

Разрешённые действия:

- постепенно повысить ставку;
- масштабировать;
- найти похожие ключи;
- сохранить текущую стратегию.

Запрещённые действия:

- минусовать;
- отключать;
- немедленно минусовать;
- немедленно отключать.

Ожидаемый эффект:

```text
Дополнительный расход = текущий расход * 20%
Дополнительный оборот = Дополнительный расход / (текущий ДРР / 100)
```

Пример:

```text
Расход = 10 000 ₽
ДРР = 25%
Дополнительный расход = 2 000 ₽
Оценочный дополнительный оборот = 2 000 / 0.25 = 8 000 ₽
```

Вопрос эксперту:

- можно ли считать 3 заказа достаточным основанием для масштабирования?
- корректен ли коэффициент +20% к расходу?
- нужно ли масштабирование ограничивать по CTR, позиции, частотности, остатку или маржинальности?

## WatchCandidate — наблюдать

Ключ получает статус `Наблюдать`, если:

```text
Заказы > 0
и ДРР рассчитан
и ДРР > 30%
и ДРР <= 36%
```

36% — это 120% от целевого ДРР 30%.

Смысл:

```text
Ключ приносит заказы, но экономика чуть хуже целевого ДРР. Резко отключать его опасно.
```

Разрешённые действия:

- наблюдать;
- собрать больше данных;
- снизить ставку осторожно.

Запрещённые действия:

- агрессивно масштабировать;
- немедленно отключать.

Ожидаемый эффект:

```text
Денежный эффект не считается. Эффект описывается как снижение риска ошибочного решения.
```

Вопрос эксперту:

- верна ли зона наблюдения `30% < ДРР <= 36%`?
- нужно ли для разных категорий делать допустимое отклонение не 20%, а другое?

## BadDrr — плохой ДРР

Ключ получает статус `Требует внимания`, если:

```text
Заказы > 0
и ДРР рассчитан
и ДРР > 36%
и Расход >= 500 ₽
и уверенность не Low
```

36% — это целевой ДРР 30% * 1.2.

Смысл:

```text
Ключ приносит заказы, но экономика заметно хуже целевого ДРР.
```

Разрешённые действия:

- снизить ставку;
- наблюдать;
- оптимизировать карточку/кампанию.

Дополнительное разрешённое действие:

```text
Рассмотреть минус-слово,
если ДРР > 45%
и заказов меньше 3.
```

45% — это целевой ДРР 30% * 1.5.

Запрещённые действия:

- повышать ставку;
- масштабировать.

Ожидаемый эффект:

```text
Оценочная экономия = Расход * 30%
```

Вопрос эксперту:

- корректно ли разделение на `наблюдать` до 36% и `требует внимания` выше 36%?
- корректна ли оценка экономии как 30% от расхода?
- нужно ли при плохом ДРР учитывать количество заказов, средний чек, маржу и повторяемость продаж?

## Neutral — без рекомендации

Ключ получает статус `Без рекомендации`, если:

- не найдено ни одного активного insight;
- по текущим правилам нет явной проблемы или точки роста.

Это не означает, что ключ хороший. Это означает только то, что текущий набор правил не нашёл оснований для действия.

## Статусы в интерфейсе

Backend-маппинг:

```text
BadSpendWithoutOrders -> К удалению
BadDrr                -> Требует внимания
ScaleCandidate        -> Эффективное
WatchCandidate        -> Наблюдать
LowData               -> Мало данных
нет insight           -> Без рекомендации
```

В таблице ключей показывается главный insight по ключу. Если у ключа несколько insights, выбирается insight с максимальным приоритетом.

Сортировка строк в overlay:

```text
1. Сначала строки с рекомендациями
2. Затем по priorityScore убыванию
3. Затем по расходу убыванию
4. Затем по фразе
```

## Приоритет рекомендаций

Backend считает числовой `PriorityScore` от 0 до 100.

Формула:

```text
RawPriorityScore =
Вес цели
* ImpactScore
* UrgencyScore
* ConfidenceScore
* SeasonScore
* StockRiskScore

PriorityScore = min(100, round(RawPriorityScore * 25))
```

Сейчас `SeasonScore` и `StockRiskScore` фактически равны 1, потому что данных об остатках и сезонности нет.

## Уровни приоритета

```text
0-29   -> Low
30-59  -> Medium
60-79  -> High
80-100 -> Critical
```

## ImpactScore

Для проблемного расхода и плохого ДРР:

```text
Расход < 300 ₽       -> 0.2
300-999 ₽            -> 0.4
1000-2999 ₽          -> 0.7
>= 3000 ₽            -> 1.0
```

Для кандидатов на масштабирование:

```text
Заказы < 3           -> 0.3
3-9 заказов          -> 0.6
10-29 заказов        -> 0.8
>= 30 заказов        -> 1.0
```

Для остальных типов по умолчанию:

```text
0.5
```

## UrgencyScore

Срочность повышается только для расхода без заказов:

```text
BadSpendWithoutOrders
и Расход >= 3000 ₽
и Заказы = 0
```

Тогда:

```text
UrgencyScore = 1.5
```

В остальных случаях:

```text
UrgencyScore = 1.0
```

## Вес цели пользователя

Пользователь передаёт цель текстом. Backend превращает её во внутренний тип.

Примеры:

```text
"снижение ДРР", "оптимизация ДРР", "дрр" -> ReduceDrr
"увеличение заказов", "рост заказов" -> IncreaseOrders
"распродажа остатков", "остат" -> SellOutStock
"удержание позиций", "позиции" -> MaintainPosition
"рост выручки", "рост прибыли" -> IncreaseRevenue
```

Если цель не распознана:

```text
IncreaseRevenue
```

Вес цели влияет на приоритет.

### Если цель — снизить ДРР

```text
Расход без заказов = 1.5
Плохой ДРР = 1.4
Наблюдать = 0.9
Масштабирование = 0.8
```

### Если цель — увеличить заказы

```text
Масштабирование = 1.5
Хороший ключ = 1.3
Плохой ДРР = 0.9
Мало данных = 0.5
```

### Если цель — рост выручки

```text
Масштабирование = 1.5
Хороший ключ = 1.4
Плохой ДРР = 0.9
Расход без заказов = 0.9
```

## Guardrails — запреты на опасные действия

Система добавляет запреты независимо от типа рекомендации.

### Не минусовать резко ключ, который конвертит

Условие:

```text
Заказы > 0
и ДРР <= 36%
```

Запрещается:

```text
Немедленное минус-слово
```

### Не масштабировать плохую экономику

Условие:

```text
ДРР > 45%
```

Запрещается:

```text
Scale
AggressiveScale
```

### Не делать жёсткие выводы при низкой уверенности

Условие:

```text
ConfidenceLevel = Low
```

Запрещается:

```text
Немедленное минус-слово
Агрессивное изменение ставки
Масштабирование
Агрессивное масштабирование
```

## Как выбирается действие для показа

Для каждого статуса есть приоритетный список действий.

### К удалению

```text
1. Рассмотреть минус-слово
2. Снизить ставку
3. Перенести в наблюдение
```

### Требует внимания

```text
1. Снизить ставку
2. Оптимизировать
3. Наблюдать
```

### Эффективное

```text
1. Масштабировать
2. Повысить ставку постепенно
3. Найти похожие ключи
4. Сохранить
```

### Наблюдать

```text
1. Наблюдать
2. Снизить ставку осторожно
3. Собрать больше данных
```

### Мало данных

```text
1. Собрать больше данных
2. Наблюдать
```

Показывается первое действие из списка, которое не запрещено guardrails.

## Роль LLM

LLM не принимает решение о том, что делать с ключом.

До LLM backend уже знает:

- тип insight;
- статус;
- рассчитанные метрики;
- приоритет;
- разрешённые действия;
- запрещённые действия;
- технический комментарий.

LLM получает только выбранные backend insights и должна:

- объяснить их человеческим языком;
- сгруппировать рекомендации;
- не пересчитывать метрики;
- не придумывать новые числа;
- не предлагать запрещённые действия.

Если LLM недоступна, backend формирует технический fallback-текст.

## Отбор insights для LLM

Перед LLM выбирается максимум 20 insights.

Порядок отбора:

```text
Top 3 Critical
Top 5 High
Top 5 ScaleCandidate
Top 5 WatchCandidate
Top 5 LowData
Затем добор лучшими по priorityScore до лимита 20
```

## Что сейчас не учитывается

Сейчас в фактической логике не используются или используются неполно:

- маржинальность товара;
- комиссия маркетплейса;
- логистика;
- цена товара;
- текущая ставка;
- позиция в выдаче как правило решения;
- частотность как правило решения;
- остатки;
- сезонность;
- цель по остаткам;
- категория товара;
- семантическая релевантность запроса;
- брендовые / небрендовые запросы;
- органические продажи;
- дневная динамика, тренд и статистическая значимость;
- разные целевые ДРР по кампаниям или товарам.

Некоторые enum-типы уже есть в коде, например `StockRisk`, `SeasonRisk`, `SemanticIrrelevant`, `GoodKeyword`, но текущий генератор keyword insights их фактически не создаёт без дополнительных данных.

## Главные вопросы эксперту

1. Подходит ли целевой ДРР 30% как дефолт, или его нужно задавать по категории/товару/марже?
2. Достаточно ли 30 кликов и 500 ₽ расхода для вывода по неэффективному ключу?
3. Корректно ли считать ключ с 3 заказами и ДРР ниже цели кандидатом на масштабирование?
4. Верна ли зона наблюдения `TargetDrr < ДРР <= TargetDrr * 1.2`?
5. Верен ли порог сильного плохого ДРР `TargetDrr * 1.5`?
6. Можно ли оценивать экономию при плохом ДРР как 30% от расхода?
7. Можно ли оценивать масштабирование как +20% расхода при сохранении текущего ДРР?
8. Какие действия должны быть при `расход есть, заказов нет`: минус-слово, снижение ставки, ожидание или проверка карточки?
9. Нужно ли разделять правила для новых кампаний и стабильных кампаний?
10. Какие дополнительные поля нужны эксперту для более корректных рекомендаций?

## Предложения для следующей версии правил

Для повышения качества рекомендаций стоит добавить:

- целевой ДРР на уровне товара/кампании;
- маржу или хотя бы целевой допустимый рекламный расход;
- цену товара и средний чек;
- текущую ставку;
- остатки и цель по распродаже;
- категорию товара;
- признак брендового/небрендового запроса;
- ручную разметку нерелевантных фраз;
- минимальный период наблюдения;
- сравнение с предыдущим периодом;
- отдельные правила для новых ключей.
