# Карта действующих рекомендаций, оценок и данных EcomAds

Дата аудита: 07.10.2026. Область: текущая версия приложения с загрузкой WB API, сводка, экран кампании, кластеры и связанная Telegram-сводка.

Дополнение после аудита: по запросу пользователя добавлены отдельные [оценочная сумма заказов и ДРР кластеров](../cluster-order-estimates.md) на основе `fullstats.sum_price / fullstats.shks` той же пары и выбранного периода. Исходная карта ниже фиксирует состояние до этого дополнения. Фактические KPI и перечисленные правила рекомендаций не изменены; оценки не восполняют отсутствие фактической выручки кластера.

## 1. Что установлено

В текущем интерфейсе работают **три типа рекомендаций**: рекламный ДРР выше цели, CTR ниже нормы, расход кластера без заказов. Сводка показывает первые два типа по кампаниям; экран кампании показывает их же и третий тип по кластерам.

Кроме рекомендаций есть четыре текстовые оценки кластеров, оценка отклонения дневного расхода, выделение KPI относительно нормы, цветовые оценки изменений KPI и статусы полноты данных. Это разные механизмы: статус строки не всегда создаёт рекомендацию.

Документ составлен по контроллерам, импортерам и React-интерфейсу. «Собирается» означает наличие реализации загрузки и хранения; это **не подтверждение наличия данных в конкретном кабинете за конкретный период**. База кабинета и актуальные ответы WB в этом аудите не проверялись. Описания ограничений относятся к подключённым источникам и текущему коду, а не ко всем возможным API WB.

Программная логика не изменялась. Исторический документ для экспертной оценки рассматривается отдельно и не считается доказательством действующего поведения.

## 2. Понятия и формулы

| Показатель | Бизнес-смысл и расчёт | Ограничение |
|---|---|---|
| `Revenue` / «Заказы с рекламы» | Сумма рекламных заказов из `fullstats.sum_price`, в рублях | Это не подтверждённая выручка от выкупленных товаров и не прибыль |
| Рекламный ДРР кампании | Сумма рекламных расходов / сумма рекламных заказов × 100% | Рассчитывается при положительной сумме заказов |
| Общий ДРР от заказов | Расход кабинета из истории затрат / сумма всех заказов кабинета × 100% | Учитывает все заказы, включая нерекламные; другой знаменатель и источник расходов |
| CTR | Сумма кликов / сумма показов × 100% | При нулевых показах осмысленной оценки нет |
| CPC | Сумма расходов / сумма кликов | При нулевых кликах не рассчитывается |
| CR | Количество заказов / клики × 100% | Рассчитывается для таблицы товаров; в рекомендациях не используется |
| CPO | Расход / количество заказов | Рассчитывается для таблицы товаров; в рекомендациях не используется |
| Кластер | Строка в разрезе кампания + артикул + название кластера | Одно название у разных товаров не объединяется в общую оценку |

KPI выбранного периода рассчитываются из сумм исходных величин, а не из среднего дневных процентов. Даты в продукте интерпретируются по МСК.

## 3. Действующие рекомендации по сводке и кампании

Общий допуск: **текущий статус кампании WB = 9 (активна)** и `coverageDays > 0`. Приостановленные кампании (11) и другие статусы не получают эти рекомендации, даже если за выбранный исторический период есть расход.

| ID | Где показывается | Точное условие | Что рекомендуем | Какие данные нужны | Данные и реализация |
|---|---|---|---|---|---|
| C1: высокий рекламный ДРР | «Требуют внимания» в сводке; «Рекомендации» кампании | `revenue > 0` и `drr > targetDrr` | Проверить ставки и состав кампании | Расход, сумма рекламных заказов, цель ДРР, статус, покрытие дней | Данные собираются; правило работает |
| C2: низкий CTR | Те же блоки | `impressions > 0` и `ctr < minCtr` | Проверить объявления и соответствие запросам | Показы, клики, норма CTR, статус, покрытие дней | Данные собираются; правило работает |

Правила независимы: одна кампания может получить обе рекомендации. Граница ДРР строго `>`, CTR строго `<`: равенство норме не вызывает рекомендацию.

Если загружены не все ожидаемые дни, рекомендации **не блокируются**, а получают пометку «Вывод предварительный». Для C1 действие дополнено указанием проверить после завершения загрузки периода; для C2 действие остаётся тем же. Минимальный расход, минимум кликов и заказов в этих правилах не проверяются.

Сортировка — по имени кампании, без оценки серьёзности или потенциальной экономии. В сводке сначала видны три карточки; остальные открываются кнопкой. Кластерные рекомендации в сводку не включаются.

Если список пуст, сводка показывает сообщение об отсутствии отклонений либо недостатке данных. Отсутствие карточек не доказывает эффективность: например, при положительном расходе и нулевой сумме заказов C1 не сработает.

Источник: [recommendations.ts](../../Ecomads.WebApplication/ClientApp/src/shared/lib/recommendations.ts), [ProjectsController.cs](../../Ecomads.WebApplication/Controllers/ProjectsController.cs), [DashboardPage.tsx](../../Ecomads.WebApplication/ClientApp/src/pages/DashboardPage/DashboardPage.tsx), [CampaignPage.tsx](../../Ecomads.WebApplication/ClientApp/src/pages/CampaignPage/CampaignPage.tsx).

## 4. Оценки строк кластеров

Для каждого сочетания артикул + кластер суммируются дневные строки за выбранный период. Расход суммируется всегда. Клики, показы, корзины и заказы становятся `null`, если хотя бы одна загруженная строка не содержит соответствующего показателя. Это не проверяет наличие всех дней периода.

Проверки выполняются **последовательно**, с возвратом первого подходящего результата:

| Порядок / ID | Текст оценки | Точное условие | Нужные данные | Следствие |
|---|---|---|---|---|
| 1 / K1 | «Показатели неполные» | Клики или заказы равны `null` | Присутствие полей кликов и заказов во всех загруженных строках | Рекомендация не создаётся |
| 2 / K2 | «Расход без заказов — проверить» | `spend >= minSpend` **и** `clicks >= minClicks` **и** `orders == 0` | Расход, клики, заказы; два порога | Может создать рекомендацию R1 ниже |
| 3 / K3 | «Недостаточно данных» | `spend < minSpend` **и** `clicks < minClicks` **и** `orders < minOrders` | Расход, клики, заказы; три порога | Рекомендация не создаётся |
| 4 / K4 | «Наблюдать: выручка кластера недоступна» | Все остальные случаи | После предыдущих проверок; выручка не передаётся в функцию оценки | Нейтральный остаточный статус; рекомендация не создаётся |

**K4 не является оценкой эффективности по экономике.** В модели кластеров поля выручки нет; эта фраза возвращается без проверки отдельного значения выручки.

Примеры при нормах 500 ₽ / 30 кликов / 3 заказа:

| Расход | Клики | Заказы | Оценка |
|---:|---:|---:|---|
| 600 ₽ | 35 | 0 | Расход без заказов — проверить |
| 100 ₽ | 10 | 0 | Недостаточно данных |
| 600 ₽ | 10 | 0 | Наблюдать: выручка кластера недоступна |
| 100 ₽ | 35 | 0 | Наблюдать: выручка кластера недоступна |
| 600 ₽ | 35 | 4 | Наблюдать: выручка кластера недоступна |
| 600 ₽ | нет значения | 0 | Показатели неполные |

Оценки строк рассчитываются и показываются независимо от текущего статуса кампании и завершённости загрузки периода. Предупреждение о неполной загрузке выводится отдельно над таблицей.

Источник: [WbCampaignClustersController.cs](../../Ecomads.WebApplication/Controllers/WbCampaignClustersController.cs), [WbClusterTable.tsx](../../Ecomads.WebApplication/ClientApp/src/pages/CampaignPage/components/WbClusterTable.tsx).

## 5. Действующая рекомендация по кластеру

| ID | Условие | Где показывается | Действие | Обеспеченность |
|---|---|---|---|---|
| R1 | Оценка K2 + текущий статус кампании 9 + `isPeriodComplete == true` | Блок «Рекомендации» на экране кампании | Проверить релевантность кластера, карточку товара и настройки рекламы в WB; указать отсутствие выручки кластера | Расход, клики и заказы собираются; правило работает при допуске |

Текущая рекомендация не предлагает автоматическое минусование, удаление кластера или изменение ставки. Текст «К удалению» из прежнего описания логики здесь не применяется.

`isPeriodComplete` сейчас устанавливается, если найдена **хотя бы одна** завершённая задача `clusters`, охватывающая весь выбранный период и содержащая хотя бы одну пару с этой кампанией. Контроллер не проверяет покрытие всех её артикулов этим условием. Несколько завершённых задач, которые вместе покрывают период, но по отдельности его не охватывают, этим условием также не объединяются.

Следствие для аудита качества: флаг завершённости задачи и полнота данных всех пар — не одно и то же. Это место требует проверки сценариев пакетной загрузки; аудит не утверждает, что ошибка уже возникла в конкретном кабинете.

Рекомендации кластеров наследуют порядок таблицы — по убыванию расхода. Общей приоритизации с рекомендациями кампании нет: сначала идут рекомендации кампании, затем кластеров.

## 6. Остальные оценки и сигналы

| ID / механизм | Условие и расчёт | Где | Данные | Является ли рекомендацией |
|---|---|---|---|---|
| E1: ДРР «Выше цели» | Положительная сумма рекламных заказов и ДРР выше цели | Таблица кампаний; цвет KPI кампании | `fullstats` + нормы | Выделение KPI; допуска по статусу 9 здесь нет |
| E2: CTR ниже нормы | Показы > 0 и CTR ниже нормы | Цвет KPI кампании | `fullstats` + нормы | Выделение KPI; отдельного допуска по статусу нет |
| E3: рост дневного расхода | Последний выбранный завершённый день / средний расход предыдущих 7 дней; изменение `>= deviationPercent` | Под графиком кампании | 8 дневных строк расходов из `CampaignStatistics` | Сигнал, без карточки и предлагаемого действия |
| E4: падение дневного расхода | То же изменение `<= -deviationPercent` | Там же | Те же данные | Сигнал; текст нейтрального цвета |
| E5: обычный расход | Изменение внутри границ | Там же | Те же данные | Числовое сравнение, без действия |
| E6: нет базы / мало дней | Нет любой из 8 дневных строк → `insufficient`; среднее предыдущих 7 дней = 0 → `no_baseline` | `no_baseline` объясняется текстом; `insufficient` не выводится отдельным текстом | Дневной расход | Ограничение оценки |
| E7: сравнение KPI с предыдущим периодом | Предыдущий период той же длины непосредственно перед текущим | KPI сводки и кампании | Данные двух периодов | Цветовая оценка динамики, без рекомендации |
| E8: общий ДРР и его доступность | История затрат / все заказы; только дни с обеими величинами | KPI и график сводки | История затрат + воронка | Метрика и статус полноты; правила превышения нормы общего ДРР нет |
| E9: Telegram «Выше цели» | Рекламный ДРР кампании > цели | Отправляемая по запросу вчерашняя сводка | `fullstats` за вчера + нормы | Список отклонений; CTR и кластеры не включаются |

E3–E6 используют конец выбранного периода, а не обязательно календарное вчера. Конец позже вчера по МСК отклоняется API. Требуются 8 дней даже при выборе короткого периода. Статус кампании не ограничивает расчёт. При нулевом среднем процент не вычисляется. Изменение округляется до двух знаков перед сравнением с порогом.

E7: рост суммы заказов и CTR оценивается положительно, снижение ДРР и CPC — положительно; изменение расхода нейтрально. Для процентных KPI выводится разница в процентных пунктах; для денежных величин — относительное изменение. При нулевой предыдущей денежной величине процент изменения не выводится. Это направление показателя, а не вывод о прибыли или причинном эффекте рекламы.

Сравнение рекламных KPI кампании доступно при полном покрытии обоих периодов (`coverageDays == expectedDays`, ожидаемых дней > 0). В сводке проверяются соответствующие кампании текущего набора в обоих периодах. Для общих заказов и расходов проверяется наличие всех дневных значений и равная длина периодов; для общего ДРР — статус `complete` обоих периодов.

E8: статус `complete` требует завершённого периода, подтверждённых расходов и заказов за каждый день и положительной суммарной суммы заказов. `preliminary` — показатель рассчитан по подтверждённым дням, но период неполный или включает текущий день. `unavailable` — показатель не удалось рассчитать. День с нулём заказов при загруженных данных учитывается; нулевой знаменатель всего периода не позволяет рассчитать ДРР.

E9 отличается от интерфейса: включает активные **и приостановленные** кампании. Перед отправкой проверяет завершённые задачи `fullstats` за вчера для всех этих кампаний и наличие их дневных строк. Выводит до 5 превышений цели по убыванию расхода, всего до 10 кампаний по расходу. Общий рекламный ДРР сообщения считается по сумме рекламных расходов и рекламных заказов этих кампаний; это не общий ДРР от всех заказов кабинета. Отправка в рамках аудита не выполнялась.

Источники: [WbSpendTrend.cs](../../Ecomads.WebApplication/Services/Wb/WbSpendTrend.cs), [WbCampaignTrendController.cs](../../Ecomads.WebApplication/Controllers/WbCampaignTrendController.cs), [kpiComparison.ts](../../Ecomads.WebApplication/ClientApp/src/shared/lib/kpiComparison.ts), компоненты KPI сводки и кампании, [WbDataCoverageService.cs](../../Ecomads.WebApplication/Services/Wb/WbDataCoverageService.cs), [TelegramController.cs](../../Ecomads.WebApplication/Controllers/TelegramController.cs).

## 7. Какие данные собираются

| Источник в текущем клиенте | Разрез хранения | Сохраняемые показатели | Применение в действующих рекомендациях | Пробелы / ограничения |
|---|---|---|---|---|
| `/adv/v3/fullstats` | Кампания × день; кампания × товар × день | Расход `sum`, сумма заказов `sum_price`, показы, клики, корзины, заказы, отмены; производные CTR, ДРР, CR, CPC, CPO | C1, C2; расход для E3–E6; Telegram | Сумма заказов не равна выкупам; корзины, заказы, отмены, CR/CPO не участвуют в C1/C2 |
| `/adv/v1/normquery/stats` | Кампания × товар × кластер × день | Расход, показы, клики, корзины, заказы, заказанные товары `shks`, средняя позиция, CPC, CPM, CTR | K1–K4, R1 | Нет поля суммы заказов / выручки кластера; часть полей допускает `null` |
| `/adv/v1/upd` | Кабинет × день, суммы по дате списания МСК | Дневной расход кабинета из `updSum`/`updTime` | Пока не участвует в C1/C2/R1 | Используется для общего расхода и общего ДРР |
| `/api/analytics/v3/sales-funnel/products` | После импорта — кабинет × день | Сумма и количество всех заказов выбранного и прошлого дня | Не участвует | Импортер суммирует товары; детализация всех заказов по товару в этой таблице не сохраняется |
| `/api/analytics/v3/sales-funnel/grouped/history` | После импорта — кабинет × день | Все заказы, открытия, корзины, выкупы и сумма выкупов | Не участвует | Показатели по всему кабинету; не атрибутированы рекламным кластерам |
| `/api/v2/search-report/product/search-texts` (Джем) | Кабинет × товар × запрос × период | Частотность, недельная частотность, средняя/медианная позиция, открытия, корзины, заказы | Не участвует | Нет суммы заказов в текущем импорте; данные товара в поиске, а не одной рекламной кампании |
| Список кампаний WB | Кампания | Статус, название, даты жизненного цикла и другие настройки клиента | Допуск активной кампании; ожидаемые дни периода | Текущий статус применяется к выбранной истории |
| Нормы пользователя | Кабинет / кампания | Цель ДРР, минимум CTR/кликов/расхода/заказов, порог отклонения, цель кампании | См. раздел 8 | Данные настроек, а не фактические показатели |

В таблице кластеров сейчас отображаются расход, показы, клики, заказы и рассчитанный из сумм CPC. Корзины возвращаются API, но в таблице не показаны. Позиция, CPM, CTR и `shks` из кластерного источника сохраняются, но в ответ таблицы кластеров не включены.

Фиолетовые частотность и позиция в таблице кластеров берутся **из Джема**, а не из сохранённой позиции рекламного кластера. Для объединения нужны совпадение периода, артикул и точное совпадение текста после обрезки пробелов и приведения регистра; интерфейс также использует признак `matchingLoadedAdCluster`. Совпадение текста не доказывает равенство рекламной атрибуции. Джем не восполняет отсутствующую сумму заказов кластера в текущей реализации.

Импортер `fullstats` требует числовые поля и отклоняет ответ без них; он не заменяет отсутствующую сумму рекламных заказов нулём. В кластерах отсутствующие дополнительные поля сохраняются как `null`. В импортере воронки отсутствующие отдельные числовые поля заменяются нулём — это отдельный риск смешения отсутствующего значения с настоящим нулём при изменении контракта ответа.

Источники: `Services/Wb/WbFullStatsImporter.cs`, `WbNormQueryImporter.cs`, `WbCostsImporter.cs`, `WbSalesFunnelImporter.cs`, `WbJamImporter.cs` и соответствующие клиенты; модели `CampaignStatistics`, `CampaignNomenclatureStatistics`, `WbClusterStatistic`, `WbStoreDailyOrders`, `WbStoreDailySpend`, `WbJamSearchQuery`.

## 8. Нормы и реально действующие настройки

Приоритет для каждого поля отдельно: **переопределение кампании → норма кабинета → значение по умолчанию**.

| Настройка | По умолчанию | Где реально используется |

Версии норм сохраняются и некоторые API возвращают их, но решения пользователя по рекомендациям привязаны к ключу рекомендации и периоду, без версии нормы или снимка исходных метрик.

## 9. Управление рекомендациями

Карточки вычисляются в React из актуального ответа статистики, а не загружаются как сохранённый результат генерации. Использования LLM в этой цепочке нет.

Доступны статусы решения: «Принял», «Отложить», «Не актуально», возврат к исходному состоянию. Сохраняются продавец, ключ рекомендации, начало/конец периода, статус и время изменения. Статус решения не меняет рекламные настройки, оценку кластера или правило отбора. Карточки после решения остаются в списке и счётчике. «Отложить» не содержит срока напоминания.

Если данные изменились или сменились нормы, карточка того же типа за тот же период может сохранить прежнее решение. Снимок доказательств решения не сохраняется. Рекомендация исчезает, когда больше не проходит условие; запись решения при этом может оставаться в базе.

Источник: [RecommendationList.tsx](../../Ecomads.WebApplication/ClientApp/src/shared/ui/RecommendationList.tsx), [WbRecommendationDecisionsController.cs](../../Ecomads.WebApplication/Controllers/WbRecommendationDecisionsController.cs).

## 10. Прежняя описанная логика и её положение сейчас

Основание: [Логика для экспертной оценки](recommendation-logic-for-marketplace-expert.md). Это описание прежнего механизма, **не действующие правила текущего интерфейса**. Пороги ниже приведены из исторического документа.

| Правило / возможность | Условие в описании | Чего требует | Текущее положение |
|---|---|---|---|
| LowData / мало данных | Клики < 30, расход < 500 ₽, заказы < 3 одновременно | Клики, расход, заказы | Аналог есть в K3, но без отдельной карточки рекомендации |
| BadSpendWithoutOrders / к удалению | Расход ≥ 500 ₽, клики ≥ 30, заказов 0 | Те же данные | Условие сохранено в K2; действие смягчено до проверки, R1 |
| ScaleCandidate / эффективное | Заказов ≥ 3, ДРР рассчитан и ≤ 30%, уверенность не Low | Заказы, расход, сумма заказов кластера, уверенность | В текущей цепочке отсутствует; не хватает суммы заказов кластера, нет расчёта уверенности |
| WatchCandidate / наблюдать по экономике | Заказы > 0 и 30% < ДРР ≤ 36% | Расход, сумма заказов кластера, заказы | Отсутствует; K4 имеет другой смысл и не является этим правилом |
| BadDrr / требует внимания | Заказы > 0, ДРР > 36%, расход ≥ 500 ₽ | Те же данные | Отсутствует на кластере; C1 на кампании использует другой уровень и границу > цели |
| Neutral | Ни одно правило не сработало | Результат предыдущих проверок | В текущем кластере заменён остаточной оценкой K4 |
| Уверенность High / Medium / Low | High: клики ≥ 100 **или** расход ≥ 3000 ₽ **или** заказы ≥ 10; Medium: ≥ 30 / ≥ 500 ₽ / ≥ 3 по тому же «или»; иначе Low | Клики, расход, заказы | Данные доступны, механизм не реализован в текущей цепочке |
| Приоритет, влияние, срочность и веса цели | Баллы и веса в историческом описании | Метрики, тип рекомендации, цель, уверенность | Не используются; текущая сортировка по имени/расходу |
| Запреты на резкое минусование / масштабирование | Зависели от заказов, ДРР и уверенности | В том числе сумма заказов кластера | Старый механизм не подключён; текущие карточки предлагают только ручную проверку |
| Экономия при проблемном расходе | Для расхода без заказов оценка до величины расхода; при плохом ДРР — 30% расхода | Расход, тип правила | Расход есть; прогнозы в текущих карточках не реализованы |
| Дополнительный оборот от масштабирования | +20% расхода / текущий ДРР | Сумма заказов кластера и рассчитанный ДРР | Не реализован, нет необходимого знаменателя на кластере |
| LLM-объяснение и отбор insights | Объяснение уже рассчитанных правил, до 20 insights | Готовые insights и ограничения действий | В текущей цепочке отсутствует; используются фиксированные тексты |

В исторической проверке выгрузки Evirma кампании 35174765 также не нашли выручку кластера: [рабочий план перехода](../scenario-plans/wb-api-transition-working-plan.md). Нельзя считать, что прежние рекомендации по ДРР были обеспечены корректной выручкой каждого кластера, без проверки старого импорта и конкретного файла. Наличие поля в старом движке и наличие значения в отчёте — разные вещи.

## 11. Карта пробелов: отсутствующие данные или отсутствующее правило

| Что хотелось бы оценить | Данные в текущей реализации | Что мешает | Возможный следующий шаг |
|---|---|---|---|
| Экономика / ДРР отдельного кластера | Расход и количество заказов есть; суммы заказов нет | **Нет необходимого показателя** | Найти и проверить источник суммы с атрибуцией кластеру, товару, кампании и периоду |
| Масштабирование и плохой ДРР кластера | Те же ограничения | **Нет показателя и нет подключённого правила** | Сначала источник, затем восстановление экономических правил |
| Кампания тратит, но не получает рекламных заказов | Расход, сумма и количество заказов собираются | **Нет отдельного правила**; C1 требует `revenue > 0` | Определить достаточность данных, задержку атрибуции и условие предупреждения |
| Уверенность / достаточность кампании для C1/C2 | Расход, клики, показы, заказы и даты собираются | **Нет допуска по объёму выборки** | Согласовать минимальную статистику и правила предварительного вывода |
| CTR, CR, CPC, CPO по кластерам | Показы, клики, расход и заказы доступны при заполненных полях | **Нет правил и норм для большинства этих метрик** | Рассчитать метрики из сумм; отдельно определить условия и действия; выручка для них не нужна |
| Воронка и отмены рекламы | Корзины, заказы, отмены есть в `fullstats`; корзины есть в кластерах | **Не используются в рекомендациях** | Определить диагнозы и достаточность выборки; не приписывать кластеру отмены кампании |
| Позиция и спрос | Позиция рекламного кластера сохраняется; частотность/позиция Джема сохраняются | **Нет правил; разный смысл источников** | Разделить рекламную позицию и поиск товара, подтвердить связь и период |
| Общий ДРР кабинета выше нормы | Общий расход и все заказы собираются | **Нет отдельной нормы/правила общего ДРР** | Не применять автоматически цель рекламного ДРР; согласовать собственный бизнес-порог |
| Прибыльность | Есть суммы заказов и расходы | **Нет связанного набора маржи, себестоимости, комиссий, логистики и выкупов нужного уровня** | Спроектировать источник экономики товара; не называть текущий ДРР оценкой прибыли |
| Остатки и доступность товара | В рассматриваемой цепочке рекомендаций не собираются | **Нет необходимых данных** | Добавить проверенный источник остатков и критерии ограничения рекламы |
| Семантическая релевантность | Название кластера и товара есть | **Нет реализованной проверки или достаточного контекста карточки** | Рекомендация «проверьте релевантность» сейчас не означает, что система обнаружила нерелевантность |
| Конкретное изменение ставки / бюджета | Некоторые настройки кампании загружаются, но рекомендации их не анализируют | **Нет обоснования оптимальной величины и механизма действия в этой цепочке** | Определить модель решения и проверяемое действие; не выдавать фиксированное изменение без основания |
| Приоритет по цели пользователя | `Goal` хранится | **Нет реализации влияния цели** | Согласовать словарь целей и правила приоритизации |

Не следует восполнять сумму заказов кластера пропорциональным распределением суммы кампании, умножением количества заказов на произвольный средний чек или подстановкой всех заказов из Джема/воронки. Без подтверждённой атрибуции это создаёт расчётную оценку, которую нельзя выдавать за фактический кластерный ДРР.

## 12. Что требует решения в первую очередь

1. Сделать K4 понятной оценкой ограничения: «Окупаемость не оценена: нет суммы заказов кластера». Отличить её от исторического «Наблюдать» по пограничному ДРР.
2. Решить, какие рекомендации должны работать по приостановленным кампаниям и историческим периодам. Сейчас допуск по текущему статусу отличается между интерфейсом и Telegram.
3. Согласовать допуск по достаточности статистики для ДРР/CTR кампании и правило «расход без рекламных заказов» на уровне кампании. Нужные фактические показатели уже собираются.
4. Проверить `isPeriodComplete` для всех пар кампания/товар и составных периодов. Разделить завершение загрузки, наличие значений, свежесть и достаточность выборки.
5. Исправить смысл сообщения «Отклонений от заданных норм нет», чтобы оно не распространялось на непроверенные правила, нулевую сумму заказов и исключённые по статусу кампании.
6. Для текущего дня единообразно учитывать предварительность: C1/C2 сейчас опираются на число строк, а не на завершённость дня. Общий ДРР учитывает незавершённый день отдельным статусом; сервис готовности отчёта проверяет обновление после закрытия дня, но в генератор C1/C2 не подключён.
7. Развивать правила без требования выручки кластера: уверенность, воронка, конверсия, позиция и спрос — после согласования порогов и бизнес-смысла каждого источника.
8. Отдельно исследовать источник атрибутированной суммы заказов кластера, если экономические рекомендации на этом уровне обязательны.

Это предложения к обсуждению, а не изменения согласованной бизнес-логики. Следующим этапом можно превратить каждый выбранный пункт в спецификацию: условие → необходимые данные → допуск по качеству → объяснение → ручное действие → критерий проверки.
