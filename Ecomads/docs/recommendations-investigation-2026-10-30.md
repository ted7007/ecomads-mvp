# Проверка рекомендаций 30.10.2026

Проверены локальные исходники, текст ТЗ v1.3 и production PostgreSQL через SSH `ecomads-new`. Запросы к БД выполнялись в `BEGIN READ ONLY`; данные, настройки и приложение не менялись. Production image: `ecomads:main-20261028T180749Z-8afd89f`. Выводы о реализации относятся к локальному коду; состояние production подтверждено SELECT-запросами.

## Почему в воронке два принятия

В кабинете с префиксом ID `218f4679` обнаружено четыре события `accepted` в `wb_snapshot_decisions`. Все четыре связаны с показами в `wb_result_exposures`: потери этих решений при сохранении не обнаружено.

| Рекомендация (префикс ID) | Принял, МСК | Последующее решение |
| --- | --- | --- |
| e6703fbc, R02, бюджет | 20.10 16:33:58 | Другого решения нет |
| 05e563a7, R03, «салфетка» | 22.10 01:46:19 | Другого решения нет |
| aeab9311, R03, «салфетницы», арт. 210787187 | 30.10 02:49:08 | «Не актуально» 30.10 02:54:46 |
| 1ed177d8, R03, «салфетницы», арт. 229356183 | 30.10 02:49:37 | «Не актуально» 30.10 02:55:38 |

`ResultsReportReader.Decision` выбирает последнее решение по рекомендации, и `Funnel.Accepted` считает только рекомендации с последним статусом `accepted`. Поэтому получается **2**, хотя события принятия было **4**. Это счётчик текущих решений, а не накопительная история принятия. Подпись «Принято» эту разницу не объясняет. Воронка дополнительно ограничивается кабинетом и датой первого показа, а не датой нажатия.

В прежней таблице `wb_recommendation_decisions` того же продавца есть ещё **3** отметки `accepted` за 03–13.10. Они выводятся отдельной историей, но не включаются в новую воронку. Всего сохранено семь отметок принятия в двух поколениях хранения; старый журнал хранит последнее решение по своему ключу и не является полным журналом нажатий. Утверждать, что любое несохранённое нажатие отсутствовало, по этим данным нельзя.

## Почему карточки возвращаются

`RecommendationService.WithDecisionsAsync` загружает решения только для текущего `RunId`. Фильтрация `irrelevant` и `snoozed` действует внутри этого расчёта. Новый расчёт той же пары «объект + правило» не наследует отказ, отсрочку или принятие. Принятая карточка также не скрывается самим фильтром.

Production подтверждает повторную обработку одной рекомендации: R03 «салфетки бумажные», ID `0c672de4`, отмечена «Не актуально» 26.10 в 01:58, 26.10 в 02:07, 27.10 в 09:23, 30.10 в 02:46 и 02:54 МСК. Последовательность соответствует отсутствию подавления между расчётами. Сами повторные нажатия не доказывают точный путь пользователя по экранам.

В результатах есть стабильный `SubjectKey` и объединение показов одной рекомендации. Но эта идентичность не используется для переноса решений и управления выдачей активных карточек. Условие повторной выдачи в `ResultsService.RegisterAsync` управляет новой записью журнала результата, а не показом карточек.

## Что считается применением

«Принял» сохраняет решение. Изменения в WB пользователь выполняет вручную. Применение определяется отдельно по снимкам после показа: минус-фразы, ставки, статус/состав кампании, бюджет. Это соответствует ТЗ.

Для кабинета `218f4679`: 24 уникальные рекомендации нового журнала, 2 с текущим решением «Принял», 10 с обнаруженным применением, 10 с текущим решением «Не актуально». Применение может обнаруживаться без принятия.

Для двух «салфетниц» при принятии предлагалось **снижение ставки на 30%**, альтернатив не было. В показах около 02:58 МСК кластеры уже исключены и карточки изменились на «Наблюдать», но применения в журнале нет. Детектор ищет именно снижение ставки для сохранённого действия; исключение не эквивалентно снижению в текущей модели. Наличие исключения подтверждено снимком карточки, но причинную связь с действиями пользователя и точный момент изменения эта проверка не устанавливала. Автоматически засчитывать любое другое действие без согласования нельзя.

Принятие R03 «салфетка» было на карточке с действием `watch`; это само по себе не является измеримым изменением. Поздний показ этой рекомендации содержит `settings_source_error`. Принятый совет R02 о бюджете имеет обнаруженное применение.

## Что требует ТЗ

Источник: `artifacts/spec-audit/recommendations-v1.3.txt`.

- §10.1, строки 445–480: принятие — ожидание изменения WB; отсрочка возвращается в указанную дату при сохранении условия; отказ возвращается не раньше 14 дней и только при удвоении рублёвой оценки; применение запускает замер; три ночи подтверждённого отсутствия условия ведут в архив.
- Строка 297: после снижения ставки повторный совет по кластеру не раньше семи дней.
- Н19, строка 736: применение определяется по снимкам независимо от кнопки «Принял»; измерение — семь полных дней после дня обнаружения, результат около Д+10.
- Н30, строки 772–774: часть жизненного цикла оставлена для уточнения — карточки без рублей, отсчёт отказа, смена нормы/версии, переходы при обнаружении действия, незавершённый замер. Недоступные данные не равны исчезновению проблемы.

Следовательно, бесконтрольный возврат отклонённых/отложенных карточек не соответствует уже описанной части ТЗ. При этом ТЗ не задаёт все условия для полного запрета любых повторов. Пробел между расчётами ранее отмечен в `docs/spec-audit-2026-10-27.md`, пункт L03.

## Логи и границы проверки

Доступны Docker-логи приложения и архивы `/opt/ecomads/logs` (согласно ops/README.md: хранение до 14 дней с лимитом объёма). История решений, показов и снимков WB в БД полезнее текстового лога для восстановления конкретного кейса.

В истории снимков настроек на момент проверки: 6326 `ready`, 64190 `source_error`, 24 `unknown` по всем кабинетам. Это накопительные количества, не частота ошибок текущего дня. Последний успешный снимок — 30.10 04:41 UTC, последний `source_error` — 30.10 03:47 UTC. Источники периодически недоступны, и это может мешать подтверждению действий. Причина конкретного ответа WB требует отдельного сопоставления с журналом запросов; её нельзя вывести из одного статуса `source_error`.

## Следующие изменения

1. Ввести жизненный цикл по стабильной идентичности рекомендации и применять его между расчётами; сохранить неизменные снимки показов.
2. Выполнить заданные ограничения отказа, отсрочки и повторного снижения; отдельно уточнить оставшиеся сценарии Н30.
3. Разделить историческое «когда-либо принято» и последнее решение либо явно переименовать существующий счётчик. Старые решения показывать с явной границей учёта.
4. Явно показывать отсутствие измеримого действия у `watch`, недоступность источника и выполнение другого действия вместо предложенного.
5. Проверить сквозные сценарии нового расчёта, изменения решения и фактического изменения WB. Не засчитывать неподтверждённое применение задним числом.
