Основной результат — компактные карточки и понятные состояния; новую серверную функциональность не внедрять внутри визуальной задачи.

## Что должно быть видно

Desktop от 1200 px: две колонки примерно 58% / 42%, выровненные сверху, отступ между карточками 16 px. Использовать действующие светлые токены; не переписывать общую тему.

Левая колонка, сверху вниз:

1. Карточка подключения WB с данными токена и действиями.
2. Отдельная карточка «Загрузка данных»: компактные строки источников и управление сбором.
3. Отдельная карточка «Подключить ещё кабинет» с короткой инструкцией и полем токена.

Правая колонка — карточка Telegram:

1. Подключённые чаты и привязка нового.
2. «Время утренней сводки» и «Уведомления» — честное обозначение отсутствующей функции без имитации работающих настроек.
3. «Как выглядит сводка» — визуальный пример, явно помеченный демонстрационным.
4. Существующая ручная отправка и свёрнутая история.

Основной заголовок страницы — `h1`, карточки — `h2`. Подзаголовки внутри карточек — `h3` или обычная подпись, без скачка к h6. Большие абзацы о методах и лимитах не занимают первый экран.

## WB-01 · Карточка кабинета: факт → план

**Факт.** Сейчас подключение, инструкции, кнопки загрузки, автосбор и весь список источников находятся в одной длинной карточке. Маска токена и статус Джема спрятаны в «Настройки подключения» в самом низу. В макете эти сведения доступны сразу; действия «Заменить токен» и «Отключить» находятся рядом с названием.

**План.**

- В шапке: имя кабинета, компактный статус, «Заменить токен», «Отключить». Ниже — строки свойств, как в макете.
- Доступные свойства: срок токена, маска `••••` + последние четыре символа, Джем и дата его проверки, число кампаний; ID продавца можно убрать в дополнительные сведения. Все даты и время показывать в МСК, а не в часовом поясе браузера.
- `jamStatus`: `active` — «Доступен» с фиолетовой меткой; `access_denied` — «Нет доступа»; `payment_required` — «Требуется подписка/оплата»; `unknown` — «Не подтверждён». Не приравнивать неизвестность к отсутствию Джема.
- Тип токена, категории и режим доступа **не возвращаются** `getWbStores`. Не печатать «Базовый / все три категории / Только чтение» как проверенные свойства сохранённого токена. Сохранить эти три строки макета с «Сведения недоступны» и короткой подсказкой; требования к создаваемому токену находятся в форме подключения. Отдельное расширение API возможно позже.
- Дата окончания — обычное свойство. Не вводить автоматические жёлтые/красные предупреждения «скоро истечёт» по новым клиентским порогам и не рассылать напоминания. Уже подтверждённый блокирующий статус `autoRefreshBlocked` показать локально с действием «Заменить токен»; не называть подключение исправным только из-за наличия строки в массиве stores.
- Замена открывает ту же карточку подключения с контекстом выбранного кабинета и переводит фокус на поле. API определяет кабинет по ID продавца в токене: честно пояснить, что тот же ID обновляет токен, другой ID добавляет кабинет. Не обещать принудительную замену конкретного ID через несуществующий endpoint.
- Отключение — короткий диалог с названием и пояснением: токен будет отключён, текущие загрузки остановятся; историю не называть удаляемой. Выполнять существующий DELETE только после действия в диалоге, блокировать повторные клики, ошибку оставлять рядом с действием.
- После подключения/замены/отключения обновить существующие кеши stores, проектов и данных соответствующего кабинета, сбросить недействительный выбор кабинета для ручной отправки. Не оставлять в панели старый статус до перезагрузки страницы.

**Приёмка.** Сведения токена находятся над загрузками. В DOM нет полного токена. `payment_required` не выглядит как `unknown`. Отмена диалога не вызывает DELETE. Нет нового предупреждения об истечении срока.

## WB-02 · Загрузка данных: факт → план

**Факт.** Каждый источник занимает несколько строк с одинаковыми пояснениями. Годовые задачи увеличивают высоту основной карточки; Telegram заканчивается значительно раньше левой колонки. Есть polling, история, повторы и пауза. Цвет метки выбирается из `lastJob`, а текст — из `activeJob ?? lastJob`: возможен зелёный статус при текущей ожидающей задаче. Подробности и действия тоже привязаны к `lastJob`.

**План.**

- Отделить в собственную карточку. В заголовке «Загрузка данных» и компактная «Обновить статус». Не подписывать весь список «за вчера»: источники имеют разные периоды.
- Основная таблица по образцу макета: **источник | последняя успешная обработка | состояние**; у строки доступно «Подробнее». Период, счётчики, причина ожидания и действия — в подробностях строки/панели. На телефоне — компактные строки с переносом, без широкой таблицы.
- Основной список — текущие источники, реально пришедшие в `overview.sources`. Месячные перепроверки и годовые виды вынести в свёрнутое «История и дополнительные загрузки» со счётчиком активных задач. Не терять неизвестный новый kind: показывать в дополнительных строках с нейтральной подписью.
- **Не копировать демонстрационные шесть строк буквально.** Для «Списка кампаний» и «Баланса и бюджетов» текущий overview не даёт самостоятельных заданий/времени. Не придумывать их готовность, количество или время из других источников. Не добавлять синтетические строки «Готово».
- Выбирать отображаемую задачу один раз: `displayJob = source.activeJob ?? source.lastJob`. Метка, цвет, прогресс, подробности и допустимые действия должны относиться к одному job.id. `lastSuccessAtUtc` остаётся отдельным временем предыдущей успешной обработки.
- Состояния: завершена — зелёная; выполняется/запрос/сохранение — синяя; очередь/пауза — нейтральная; лимит/повтор — янтарная; подтверждённая ошибка — красная; нет задания — «Ещё не запускалось». Цвет сопровождается текстом. «Обработка завершена» не означает, что данные за весь период полны.
- Прогресс показывать в родных единицах API: кампании/товары/пары/запросы. Не превращать его в «N из 90 дней». Если totalCount неизвестен/равен нулю — не рисовать 100% и не делить на ноль. Время завершения только из серверной оценки и с «примерно».
- «Загрузить всё из WB» и «Загрузить историю за год» сохранить компактным рядом управления внутри этой карточки. Сохранить действующие ограничения повторного запуска; не добавлять прямые вызовы WB в обход очереди.
- Автосбор — один переключатель плюс одна короткая строка расписания. Сохранить `autoRefreshEnabled`, `autoRefreshAvailable`, `autoRefreshBlocked` как разные состояния. Если автосбор недоступен на сервере — переключатель disabled с пояснением; отображаемое значение не менять до успешного PUT либо откатывать оптимистическое значение при ошибке.
- Расписание: действующие 06:15/18:15 МСК и значение `nextAutoRefreshAtUtc`. Не переносить из макета «01:00» и обещание готовности к определённому часу. Различать время постановки задачи и время готовности данных.
- Длинные объяснения периодов, месячной проверки, очереди и годовой истории — одно свёрнутое «Как работает загрузка». Ошибка действия/блокировка с понятным исправлением остаётся локально видимой; шумные повторяющиеся уведомления о неполноте не возвращать.
- Сохранить паузу/продолжение только для поддержанных годовых kinds, retry — только по `canRetry`. Ошибка retry/pause должна быть видна сразу после клика, даже если подробности закрыты.
- Сохранить polling 15 сек при активной работе / 60 сек без неё, без опроса в фоне; не выполнять новый запуск сборов при обновлении статуса или переключении строк. Исправление кешей не должно создавать бесконечную цепочку refetch.

**Приёмка.** При старой завершённой и новой ожидающей задаче основной статус не зелёный; действия используют ID новой задачи. Из таблицы доступны все существующие сценарии, но инструкции и девять подробных блоков не занимают основной экран.

## WB-03 · Журнал загрузок: факт → план

**Факт.** Уже свёрнут, фильтруется сервером по kind/status, страницы по 10. API сортирует по CreatedAtUtc DESC, затем Id DESC, параметра сортировки нет.

**План.**

- Оставить свёрнутым внутри загрузок. Фильтры «Источник» и «Состояние», понятная подпись «Сначала новые», страницы по 10.
- Не добавлять кликабельную клиентскую сортировку одной загруженной страницы: она создаст ложный общий порядок. Произвольная сортировка журнала — отдельное расширение API.
- При изменении фильтра/кабинета сбросить страницу и открытые подробности; корректно зажать номер страницы при уменьшении total. Запросы всегда включают storeId.
- Различать загрузку, пустой ответ и ошибку с локальным повтором. Историю можно запрашивать только после раскрытия, сохранив актуализацию при открытом журнале и активном job.

## WB-04 · Подключение токена: факт → план

**Факт.** Для существующего кабинета форма скрыта за общей кнопкой. В макете есть самостоятельная третья карточка с четырьмя шагами и полем. Текущая инструкция короче; сервер уже проверяет JWT и пробный запрос WB.

**План.**

- Постоянная компактная карточка «Подключить ещё кабинет», при отсутствии кабинетов — «Подключить кабинет WB». Для режима замены — название кабинета и кнопка отмены режима.
- Короткие четыре шага по макету: создать отдельный базовый токен; нужные категории; только чтение и выключенный тестовый контур; вставить в EcomAds. Детальное объяснение категорий — в подсказке/раскрытии.
- Не менять серверные правила: сейчас обязательны Продвижение и Только чтение; отсутствие Аналитики/Статистики не повод добавлять новую клиентскую блокировку. Не утверждать, что все категории проверены, если ответ их не содержит.
- Поле password, autoComplete off, без сохранения в URL/localStorage/логах/аналитике. Только trim и проверка непустоты на клиенте; окончательная валидация серверная. Маску старого токена не подставлять как новый токен.
- «Проверить и подключить», pending, локальная ошибка; успех очищает поле и обновляет список. Не стирать введённое значение при ошибке. При закрытии/отмене режима очистить секрет.
- Сохранить обработку конфликта 409 и ошибки проверки WB 422. Не разлогинивать EcomAds из-за отказа WB, серверный маппинг статусов не менять.

## TG-01 · Чаты и привязка: факт → план

**Факт.** Есть список, создание одноразовой ссылки, переход к боту и ручная проверка привязки. Нет отдельного статуса карточки; история и отправки постоянно раскрыты. В API есть displayName, но нет отдельного @username или связи «чат → кабинет».

**План.**

- Заголовок Telegram, краткий статус; подзаголовок «Подключённые чаты», строки с мягкой заливкой как в макете. Имя — `displayName` или «Личный чат», без выдуманного username.
- «Подключить ещё чат» / «Подключить Telegram» вызывает существующий `createTelegramLink`. До ответа не создавать самодельный deep link. Имя бота — из `botUsername`, ссылка — из `linkUrl`; если URL отсутствует, сохранить инструкцию с `/start code`.
- Ссылка живёт до `expiresAtUtc`, а не 15 минут с момента рендера. Показывать срок в МСК. Истёкшую ссылку не представлять действующей; предложить создать новую. Не делать повторный POST автоматически.
- Сохранить кнопку «Я привязал чат — проверить»; после успешной проверки обновить список и убрать использованный код из основного интерфейса. Не объявлять привязку успешной только после открытия Telegram.
- При `botConfigured=false` — локальное сообщение о недоступности, без активных кнопок создания ссылки/отправки. Loading/error не равны «Чатов нет»; при ошибке — повтор.
- Чаты принадлежат аккаунту EcomAds; отправка по выбранному кабинету идёт в подключённые чаты аккаунта. Не рисовать несуществующие индивидуальные маршруты доставки на чаты.
- Отключение чата — диалог с именем, существующий DELETE, локальный pending/error. Никаких отправок во время открытия/отрисовки карточки.

## TG-02 · Время и уведомления: факт → план

**Факт.** Макет содержит время утренней сводки и четыре checkbox: утренняя сводка; бюджет/баланс; токен; данные за вчера. ТЗ описывает эти функции. В текущем API страницы нет GET/PUT этих настроек; интерфейс прямо сообщает, что утреннее расписание и бюджетные уведомления пока не подключены.

**План текущей задачи.**

- Сохранить соответствующие заголовки/место внутри Telegram, но вместо активных select/checkbox — компактные информационные строки «Автоматическая утренняя сводка пока недоступна» и «Настройка уведомлений пока недоступна». Детали планируемых типов можно свернуть.
- Не выставлять 09:00 как якобы сохранённое значение, не показывать включённые галочки, не сохранять выбор только локально, не обещать пользователю автоматическую доставку.
- Рабочую ручную отправку разместить сразу рядом с этим пояснением. Не добавлять предупреждения об истечении токена ни в сводку, ни в верх страницы.

**Отдельная будущая задача, не часть исполнения:** контракт и хранение расписания/настроек, реальный планировщик Telegram и типы уведомлений. После этого заменить информационные строки рабочими контролами. В текущей UI-задаче запрещено создавать endpoint, миграцию или фоновую рассылку ради совпадения с картинкой.

## TG-03 · Пример сводки: факт → план

**Факт.** В макете есть блок «Как выглядит сводка», в текущей странице его нет. Формат фактически отправляемого сообщения задаёт `TelegramSummaryFormatter`, а макет содержит дополнительные сравнения и рекомендации, которых форматтер сейчас не формирует.

**План.**

- Добавить визуальную карточку предпросмотра в стиле Telegram: светло-голубая подложка, компактный текст, выделение ключевых чисел. Обязательная метка «Пример · демонстрационные данные».
- Показывать поля текущего форматтера: кабинет и дата; расход кабинета/все заказы/общий ДРР при наличии; рекламные итоги; несколько кампаний; ссылка. Не подписывать рекламный ДРР общим и не выдавать макетные проценты сравнения за реальные.
- Не добавлять в пример обещание работающего блока «Требуют внимания», автоматических алертов и кнопок решений, пока их нет в реальном шаблоне отправки. Различие с макетом зафиксировать в отчёте, а не менять backend молча.
- Предпросмотр не вызывает отправку. «Отправить тестовое сообщение» — отдельное явное действие, существующий API и подпись, что сообщение демонстрационное. При отсутствии чатов кнопка disabled с пояснением.

## TG-04 · Ручные отправки и история: факт → план

**Факт.** Есть вчерашняя сводка, период, тест и история. Фильтр периода перегружает узкую колонку. Отправка за период не обновляет кеш истории; история не имеет собственных loading/error. Результаты прошлой отправки могут остаться после переключения кабинета. Сервер истории возвращает до 30 событий, без storeId и пагинации; периодные отправки в эту историю не записываются.

**План.**

- «Отправить вчерашнюю сводку» — основное ручное действие; «За другой период» — свёрнутый подраздел. Там компактные поля дат или компактный PeriodFilter без режимов, заведомо выходящих за ограничения API.
- Для одного кабинета показывать его название; для нескольких — явный выбор по store.id. При отсутствии кабинетов отправка недоступна с пояснением. При отсутствии чатов тоже disabled.
- Сохранить валидацию включительно 1–31 день, обе даты заданы, конец не раньше начала и строго раньше `moscowToday()`. Не отправлять сегодня и незавершённые дни.
- Никаких автоматических отправок при выборе дат, кабинета, раскрытии формы и повторном открытии страницы. Один клик — один запрос; на время отправки блокировать конкурирующие кнопки отправки, чтобы не создавать дубли.
- Сохранить результаты `sent/skipped/failed/unknown/partial`: зелёный только при подтверждённой доставке без проблем; уже отправлено — нейтрально; сбой, неизвестный исход и частичная сводка — янтарно с пояснением. Не повторять unknown автоматически. HTTP 409 — существующий диалог «Сводку пока нельзя отправить» с причиной.
- Результат содержит название кабинета и даты именно выполненного запроса. При переключении кабинета/периода сбрасывать несоответствующий feedback; ответ медленного запроса не выдавать за результат нового выбора.
- История — свёрнутая, по умолчанию 5 событий с пагинацией 5/10/20/100 **внутри полученных максимум 30 событий**. Подпись «Последние отправки за день», не «Вся история». Сортировать весь полученный список до пагинации: дата отчёта, время изменения, имя кабинета; дата/число сортируются по значению. По умолчанию lastAtUtc DESC. В мобильной версии — карточки.
- Не фильтровать историю строго по текущему кабинету через storeName: одинаковые названия допустимы, storeId в ответе отсутствует. Показывать общую историю с именами. React key не должен склеивать события одинаковых имён/дат в одну строку.
- Внутри события оставить все статусы чатов и errorCode в подробностях. Добавить loading/error/retry независимо от списка чатов. Обновлять релевантные кеши после операций; не вставлять периодную отправку в историю искусственно, сервер её не хранит.

## Адаптация и визуальные правила

- Повторно использовать lightUiTokens, PageHeader, стандартные Card/Chip/кнопки и PaginationBar. Не менять глобальный sidebar ради селектора INSHIRO из макета: общего выбора кабинета сейчас нет. Для этой страницы разрешён собственный выбор кабинета.
- Несколько кабинетов: компактный селектор над тремя карточками слева, единый selectedStoreId для WB-карточки, загрузок и ручной сводки Telegram. Выбранное имя видно рядом с отправкой. Чаты и история остаются общими. При удалении выбранного — безопасный переход к доступному; при пустом списке — форма подключения. Не рендерить огромную тройку карточек для каждого кабинета подряд.
- До 1200 px — один столбец: подключение WB → загрузки → подключение ещё кабинета → Telegram. Подробности загрузок и инструкции свёрнуты, чтобы Telegram оставался достижимым. На 390 px поля и основные действия по ширине, служебные кнопки переносятся; названия/маски не вылезают за экран.
- Длинные списки чатов: после пяти строк «Показать все (N)», без потери доступа к остальным. Для управления чатами не нужны бессмысленные сортировки по статусу доставки: статус доставки относится к конкретной отправке, не к самому чату.
- Заголовки таблиц кликабельны только при настоящей сортировке всего доступного набора. Основные источники имеют фиксированный смысловой порядок, журнал WB — серверный порядок; стрелки сортировки там не рисовать.
- Цвета статусов из действующих токенов: зелёный успех, синий активность, янтарный ожидание/ограничение, красный ошибка, серый неизвестность, фиолетовый Джем. Не заливать большие карточки сплошным ярким цветом.
- Focus, label/aria-label у полей/фильтров, доступный статус pending, восстановление фокуса после диалогов. Состояния API независимы: ошибка Telegram не прячет WB, ошибка журнала не прячет сводку загрузок.

## Проверки и критерии готовности

- TypeScript + Vite, вывод сборки в ignored `artifacts/build-check-stores/dist`, а не tracked wwwroot. Существующие тесты сводки и кампании не ломаются.
- Логические тесты: displayJob выбирает active при старом completed; состояния/цвета и canRetry/paused; неизвестный total; валидация периода на границе 31/32 дней и вчера/сегодня МСК; сортировка истории до пагинации и одинаковые storeName/reportDate.
- Локальный fixture-сервер с полными Zod-ответами; реальные POST/PUT/DELETE и рассылки не использовать для QA. Проверять количество mutations: раскрытие/выбор/отрисовка — ноль; явная кнопка — один запрос.
- Состояния WB: пусто, один, несколько; истёкший/блокированный токен; недоступный/выключенный автосбор; Джем active/unknown/access_denied/payment_required; активная задача поверх completed; лимит/пауза/ошибка/неизвестный total; пустая и ошибочная история.
- Состояния Telegram: бот не настроен; нет чатов; много чатов; новая/истёкшая ссылка; linkUrl=null; ошибки GET; failed/unknown/skipped/partial/409 при отправке; потеря выбранного кабинета и медленный ответ после смены выбора.
- Визуал: 1440 × 1000, 1280 × 900, 390 × 844. Отдельные кадры: верх с обеими колонками; компактные загрузки; форма токена; Telegram с примером; история/подробности; телефон. Ни одного обязательного свойства токена после длинного списка загрузок, никаких fake-checkbox настроек и горизонтального переполнения страницы.
- Отчёт по блокам: реализовано/ограничено контрактом; ссылки на скриншоты. Не объявлять будущие расписание/уведомления рабочими. Для live-проверки после отдельного деплоя достаточно read-only health и сверки сборки; реальные сообщения не отправлять без отдельного запроса пользователя.
