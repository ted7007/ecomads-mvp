# План первого спринта рекомендательной системы EcomAds

Дата: 12 октября 2026 года. План уточнён решениями пользователя. Реализация описана в `docs/recommendations-sprint-1.md`.

Источники: `D:/Downloads/EcomAds-Unified-Recommendations-Spec-v1.docx` и `D:/Downloads/EcomAds-Recommendations-Sprints-v1.docx`. Единое ТЗ определяет поведение, документ спринтов — границы инкремента. Старые документы движка в репозитории не являются источником новых требований. Приоритет имеют согласованные в чате решения ниже. Остальные Н01–Н30 не считаются автоматически согласованными.

## 1. Результат и границы

Первый спринт — рабочий вертикальный срез: загрузка → пригодность данных → экономика → правила № 3 и № 6 → диагностические карточки → проверяемые показатели таблицы.

На экране кампании доступны:

- № 3 «Кластер без заказанных единиц»: расход, Q = 0, индивидуальный порог и осторожное предложение проверить кластер.
- № 6 «ДРР кластера выше нормы»: оценочный ДРР, сценарный диапазон, норма и предложение проверить расходы, ставку и карточку без точного изменения настройки.
- Пользовательский запрос передаёт startDate/endDate. Все факты, средняя цена, пороги и рекомендации считаются строго за эти даты по МСК; смена периода пересчитывает рекомендации.
- Состояния отсутствующих данных, недоступной экономики и недостаточного объёма наблюдений; отсутствие отклонений показывается отдельно.
- Таблица с S/I/C/A/O/Q и оценочными R̂/D̂, с возможностью открыть ровно окно рекомендации.

Не включать: точные ставки и исключения, рост, историческую авто-норму, расширение анализа до 30 дней, режим запуска и цели как полноценные политики, диагностику воронки/динамики, новые сводки кабинета, пакеты, LLM, Джем-правила, остатки, бюджет, Telegram, пользовательский жизненный цикл и результаты. Имеющиеся независимые функции сервиса сохраняются.

Решение пользователя от 13 октября 2026 года: пилоты и списки разрешённых кабинетов исключены. Новые рекомендации включены по умолчанию для всех подключённых кабинетов. Недоступные данные показываются с причиной, расчёты помечаются предварительными. Политики запуска товара и точные действия остаются в следующих спринтах.

## 2. Основа в текущем проекте

Стек: ASP.NET Core / .NET 10, EF Core / PostgreSQL, React / TypeScript / MUI, React Query и Zod. Отдельный сервис, очередь сообщений или новый frontend-фреймворк не требуются.

Уже есть:

- Импорт fullstats и дневных кластеров; товарный и кластерный `shks` сохраняются отдельно от `orders`.
- `WbClusterOrderEstimateCalculator`: взвешенная средняя, оценочная сумма, ДРР и проверки отсутствующих единиц; unit/integration-тесты.
- Планировщик загрузок, обработка задач, интервалы источников, дневные проверки кампаний.
- Нормы кабинета и кампании с ревизиями; базовое хранение решений пользователя.
- Таблица кластеров и старые рекомендации, часть логики которых находится в React.

Существенные изменения:

- Штатный `EnqueueClustersAsync(store, runId, ...)` запрашивает последние 7 дней. Для фонового окна 14 дней нужны два семидневных интервала; пользовательские периоды проверяются по фактически загруженному покрытию.
- `WbCampaignClustersController.isPeriodComplete` ищет одну покрывающую задачу; расчёт оценок внутри того же контроллера уже объединяет интервалы по паре. Эту логику нужно сделать общей и использовать для новых правил.
- Расчёт ДРР сейчас возвращает округлённые проценты. Правилам нужны неокруглённые decimal-доли.
- Норма кабинета по умолчанию сейчас 30%, товарного уровня нет. Новому движку нужен явный источник нормы и fallback 20% без перезаписи сохранённых значений.
- Отсутствующие числовые поля fullstats в ряде мест превращаются в ноль. Пригодность входов новых правил должна отличать неизвестные S/R/O от подтверждённых нулей.
- Модель кластеров хранит название, но не устойчивый WB ID. Нельзя обещать перенос истории при переименовании.

Основные точки интеграции: `Services/Wb/WbClusterOrderEstimate.cs`, `Controllers/WbCampaignClustersController.cs`, существующий `Services/Wb/WbSyncPlanner.cs`. Новый модуль разместить в `Services/Recommendations`, не наращивать контроллер бизнес-правилами.

## 3. Принятые решения и технические проверки

Пользователь 12 октября 2026 года принял следующие уточнения: весь расчёт за переданный период; денежный порог без ожидания 30 кликов; предварительные карточки во всех подключённых кабинетах разрешены с пометкой и без точных действий. Эти решения изменяют исходные требования фиксированного окна и отдельной P30.

| Вопрос | Решение или техническая проверка для спринта 1 | Статус |
|---|---|---|
| Н01: средние и границы | Принято: P = ΣR / ΣQ строго за переданный период; одна P используется для экономики и допустимого расхода. Другого окна и незаметного fallback нет | Решено пользователем |
| Н03: единицы | UI: «Заказы» для O, «Заказанные единицы» для Q, «Допустимый расход на единицу» для ДЦЗ; тест № 6 называется «+1 единица» | Подписи и приёмочные примеры; остатки в этот спринт не входят |
| Н04: зрелость | Принято: во всех подключённых кабинетах разрешены предварительные диагностические карточки при полной загрузке. Собирать версии O/Q/R. До проверенного алгоритма зрелость unverified; текущий день open_day | Не блокирует выпуск; точные действия остаются на следующих спринтах |
| Н26: источники | Проверить fullstats/normquery: поля, отсутствие строк, даты, ограничения и сопоставимость. Не подключать источники последующих спринтов | Допуск конкретного источника и правила |
| Н12: старые пороги | Принято: № 3 не ждёт 30 кликов; используются Q = 0 и max(2 × P × N; 300 ₽). Старые 500 ₽ не добавляются скрытым общим фильтром | Решено пользователем |
| Н05/Н24: минимальный UI | Карточки и таблица используют переданный период; различать отсутствие отклонений, нехватку наблюдений и отсутствие проверки. Без прогноза «через N дней появится совет» | Техническая реализация |

Для Н04 дополнительно согласовать формулу при нулевой базе, число успешных последовательных проверок, гранулярность и поздние корректировки старше 7 дней. Пока этого нет, запрещено называть данные зрелыми только по возрасту.

Для Н26 сохранить небольшой отчёт проверки источников. Официальные материалы WB подтверждают, что для CPC-кампаний некоторые метрики показов могут отсутствовать; это не основание блокировать независимые правила по S/Q/R: https://dev.wildberries.ru/en/release-notes?id=373 . Актуальные лимиты проверить по типу токена, не брать случайные числа из старого ТЗ.

Н08/Н09 не блокируют диагностическую версию: документ спринтов явно допускает её без точных действий. Остальные открытые вопросы последующих релизов не решать внутри этого спринта.

## 4. Архитектура с учётом следующих спринтов

Поток: хранилище статистики → сбор фактов → нормы и окна → качество входов → независимые правила → формирование карточек → сохранение завершённого расчёта → API → React.

1. **Сбор фактов отдельно от правил.** Пакетно загружать данные кампаний/товаров/кластеров; не выполнять запрос к БД на каждый кластер. Правила получают неизменный типизированный контекст и не обращаются к WB, БД или текущим часам.
2. **Общий расчёт экономики.** Внутри движка денежные значения decimal, ДРР и N — доли. Старый API таблицы сохраняет проценты через явный адаптер. Не сравнивать порог с округлённым `estimatedDrr`.
3. **Версионируемые политики.** Разделить окно, выбор нормы, качество источника и определения правил. Реализовать только политики первого спринта; сохранить возможность добавить историческую норму, операционные ограничения, классификацию и отбор основного действия позднее.
4. **Два независимых результата.** Вычисление предиката и разрешение показа/действия — разные поля. Например, исторически высокий ДРР можно вычислить для диагностики, но при неподтверждённой зрелости он не становится готовым действием.
5. **Правило расширяется через реестр.** Стабильные ID `R03`/`R06` соответствуют № 3/№ 6; версия, группа, требуемые факты, enabled, free/pro, шаблон объяснения. В первом выпуске доступ бесплатно. Пропуск одного правила не прекращает весь расчёт.
6. **Минимальный журнал расчётов сейчас.** Отдельные `runId` и `evaluationId`, версия схемы/правил/настроек, входные агрегаты, окна, качество и результат. Завершённая запись не переписывается; текущая выдача указывает на последний завершённый расчёт. Это технический журнал, не полная модель показов, решений или результатов из спринта 5.
7. **Изоляция и идентичность.** Ключ содержит SellerId, StoreId, CampaignId, товар и локальный ключ кластера. Для текущего источника ключ строится из точного имени после существующей очистки пробелов; хранится исходное имя, проверяются коллизии. Не объединять похожие имена и не переносить старые решения. Место для внешнего устойчивого ID добавляется без изменения адресации журнала.
8. **Никаких заготовок на все будущие сущности.** Не создавать сейчас таблицы результатов, ставок, брендов и исключений. Будущие снимки и решения смогут ссылаться на evaluationId; правила применения и хранения по Н22 остаются отдельной задачей спринта 5.

Предлагаемый срок хранения технических расчётов — 90 дней с конфигурируемой очисткой. Это отдельная техническая настройка, не политика хранения будущих решений пользователя; для будущих пользовательских решений определить отдельную политику.

## 5. Задачи первого спринта

Оценки — человеко-дни разработки с локальными проверками, ориентировочно для одного разработчика, знакомого с проектом. Ожидание решений и накопление реальных ночных наблюдений в них не входят.

### S1-01. Зафиксировать контракт первого среза — 1–2 дня

- Оформить решения из раздела 3 с датой и ответственным; отделить принятые решения от предложений.
- Составить матрицу зависимостей полей для № 3/№ 6 и небольшой набор эталонных примеров.
- Провести Н26 по двум используемым источникам на документации и обезличенных ответах. Новые запросы WB выполнять только в рамках согласованного диагностического доступа, без изменений в WB.
- Зафиксировать гранулярность полноты и исходную семантику отсутствующих строк; равенство сумм кластеров и товара не использовать как обязательное условие.

Готово: для каждого предиката известны единицы, окна и обязательные данные; каждый открытый вопрос имеет явно отключённую зависимую возможность. Независимый каркас можно делать до завершения согласования.

### S1-02. Выделить точные вычисления и контракты — 1,5–2 дня

- Вынести общие агрегации и расчёты из контроллера/округляющего адаптера в чистые функции.
- Ввести `AnalysisWindow`, `RecommendationSubject`, `RecommendationFacts`, `ResolvedNorm`, `RuleEvaluation`, машинные коды причин и человекочитаемые шаблоны.
- Использовать одну P за переданный период; учитывать все приложения fullstats только на листовом товарном уровне.
- Существующий расчёт таблицы сохранить совместимым по формату; новый движок использует неокруглённый результат.

Готово: P/R̂/D̂/Dmin/Dmax и D̂_plus воспроизводимы без БД; таблица не меняет единицы API; отсутствующие поля не восстанавливаются через другие метрики.

### S1-03. Подготовить данные и отдельный допуск качества — 3–4 дня

- Считать пользовательские периоды из существующей статистики, без запросов в WB при открытии карточек. Для фонового окна 14 дней использовать месячный fullstats и дозагрузку недостающих семидневных интервалов кластеров через существующую очередь.
- Повторно загружать последние 7 дней для наблюдения корректировок. Заполнение пропусков и повторная проверка уже загруженных дней — разные операции.
- Проверять объединение успешных интервалов по источнику, кампании и товару. Флаг `isPeriodComplete` одной задачи не использовать как допуск нового движка.
- Добавить данные качества необходимых полей fullstats: неизвестные/отсутствующие R/S/O не считать подтверждённым нулём. Для старых строк без доказательства качества сохранять `unknown`, запрашивать обновление; не менять массово существующие KPI.
- Сохранять наблюдения O/Q/R и время каждой успешной повторной загрузки на гранулярности из Н04. Ошибка загрузки не является нулевым наблюдением.
- Выделить `complete/incomplete`, `mature/unverified/immature`, достаточность выборки и сопоставимость как независимые признаки.
- При пустом ответе подтверждать нулевую активность только в рамках проверенного контракта источника; не создавать «нулевые» кластеры по отсутствию строк.

Готово: новый кабинет может получить необходимые окна; два успешных интервала объединяются; один отсутствующий день/товар обнаруживается; сбой WB не выглядит как отсутствие проблемы. Повторный импорт остаётся идемпотентным.

### S1-04. Реализовать выбор нормы — 1,5–2 дня

- Порядок: явная норма товара в кампании → кампании → кабинета → временные 20%.
- Добавить минимальное товарное переопределение N с возвратом к наследованию, проверкой принадлежности, версией и записью ревизии; остальные нормы товара пока не нужны.
- Сохранить существующие записанные нормы, в том числе 30%. Не считать отсутствие записи явным пользовательским выбором 30%.
- Возвращать источник, значение и версии нормы в расчёте и UI. Согласовать эффективную норму новой карточки и экрана «Нормы», исключить разные fallback на двух экранах.
- После изменения нормы инвалидировать клиентский запрос: выбранный период пересчитывается при следующем чтении, фоновые периоды — при следующем проходе. Во время запроса помечать пересчёт, старые снимки не менять.

Готово: наследование проверено на всех трёх уровнях; сброс переопределения работает; 20% применяется только при отсутствии явных значений; историческая авто-норма не включена.

### S1-05. Реализовать правила № 3 и № 6 — 1–1,5 дня

- № 3: Q = 0 и S ≥ max(2 × P × N; 300 ₽). При недоступной P не заменять порог на 300 ₽. Минимальные клики не требуются по решению пользователя.
- № 6: Q ≥ 3, Dmin > N и S / ((Q + 1) × P) > N. Равенство N не проходит строгую проверку.
- Наличие O, I, C или A не требовать для правила, которое их не использует. Отсутствующий Q не равен нулю.
- Возвращать `triggered`, `not_triggered` или `skipped` с причинами и фактами; для отключённого правила отдельный признак enabled.
- Выдавать только диагностические тексты. Никакой суммы экономии, назначения ставки, минуса или обещания прибыльности.

Готово: положительный, отрицательный и недоступный сценарии каждого правила проходят; один объект не получает две карточки № 3/№ 6, поскольку условия Q взаимоисключающие.

### S1-06. Расчёт периода, фоновый запуск, журнал и API — 2–3 дня

- API рассчитывает переданные startDate/endDate из БД. Фоновый проход использует отдельное стандартное окно D−15 … D−2 после ночного слота и повторяет расчёт при изменении статистики; оно не подменяет запрос пользователя.
- Закреплять дату расчёта и окно в задании. Долгая загрузка после полуночи не должна незаметно сдвигать окно начатого прогона.
- Повторная доставка/перезапуск не создаёт дубли; входная ревизия данных, политики, правил и норм определяет новое вычисление. Ошибка БД/процесса не публикует половину результата.
- Сохранять журнал и атомарно переключать текущий завершённый прогон. При сбое показывать прежний с явными датой и признаком устаревания; завершённый расчёт с неполными данными публикует именно ограничения качества, а не устаревшие уверенные карточки.
- Добавить `GET /api/wb/campaigns/{campaignId}/recommendations?startDate=...&endDate=...`: обязательный период 1–366 дней, расчёт и версия фактов, нормы, карточки и причины пропуска. Повтор одинаковых входов использует существующий run.
- Табличные агрегаты возвращать в том же ответе, что карточки. Добавить GET /recommendations/runs/{runId} для неизменного снимка; проверять принадлежность продавцу и кампании.
- DTO: `runId`, `evaluationId`, `subject`, `ruleId`, `ruleVersion`, `analysisWindow`, окна цены, `facts`, `norm`, `thresholds`, `quality`, `reasonCodes`, `explanation`, `actionKind=review`, `calculatedAt`, `schemaVersion`. Полей денежного эффекта в этом срезе нет.
- Покрытие enabled/evaluated/triggered/skipped, время расчёта и причины пропусков доступны во внутренних логах/ответе. Не строить отдельную админку.

Готово: одна и та же сохранённая версия объясняет карточку и проверочную таблицу; повтор и сбой безопасны; нет запросов в WB при открытии списка рекомендаций; запрос чужого кабинета не раскрывает наличие его результатов.

### S1-07. Подключить интерфейс кампании — 2–3 дня

- React получает новые карточки с сервера и не вычисляет их условия. Включённый флаг заменяет старую кластерную генерацию, а не добавляет дубль рядом.
- На карточке: правило, товар/кластер, окно, расход/Q, N и её источник, порог либо D̂ и диапазон, ограничения качества, диагностическое действие.
- Таблица кластеров и карточки отображают один серверный run. Фильтр периода пересчитывает оба представления; прежние данные не подставляются рядом с новыми датами.
- В таблице добавить корзины и заказанные единицы, сохранить заказы отдельно; оценки помечать словом «Оценка». Не смешивать новый маркер с устаревшей оценкой, вычисленной по другим условиям.
- Список сортировать по группе № 3 перед № 6, затем по расходу убыванию и устойчивому ключу. Расход не называть ожидаемой экономией. Это временный порядок без денежной модели Н23.
- В новых карточках пока нет кнопок жизненного цикла. Старые решения не переносить по совпадению имени или legacy-хэша; вне нового среза существующие функции остаются доступными.
- Добавить минимальное изменение/сброс товарной нормы в существующем интерфейсе норм или контексте товара, без отдельного большого экрана.

Готово: смена периода пересчитывает карточки и таблицу; снимок старого run остаётся неизменным, null не рисуется нулём, источники нормы и причины пустой выдачи понятны.

### S1-08. Сквозная приёмка и запуск — 2–3 дня

- Прогнать имеющиеся тесты импортёров, оценок, контроллеров и интеграций PostgreSQL; добавить проверки новых правил, миграций, планирования, авторизации и повторного запуска.
- Выполнить frontend build, проверить визуально экран кампании и нормы; один сквозной сценарий карточка → данные расчёта → изменение нормы → пересчёт.
- На обезличенной реальной выборке сверить суммы, покрытие и несколько срабатываний вручную. Не называть расчёт на старой статистике полноценным историческим backtest, если прошлые нормы и ревизии источника неизвестны.
- Зафиксировать результаты по каждому правилу: evaluated/triggered/skipped и причины, длительность прогона, ограничения источников.
- Включить рекомендации по умолчанию для всех подключённых кабинетов. Проверить общий технический выключатель, не удаляя статистику и журнал.

Готово: пройдены критерии раздела 7, создан короткий отчёт по данным и список оставшихся ограничений; списки кабинетов и отдельная стадия пилота не требуются.

## 6. Порядок и зависимости

Критический путь: S1-01 → S1-02 → S1-03/S1-04 → S1-05 → S1-06 → S1-07 → S1-08.

Каркас S1-02 можно начать до закрытия бизнес-вопросов. После его контрактов S1-03 и S1-04 независимы; UI может готовиться на согласованных фикстурах API. Контрактные тесты пишутся в соответствующих задачах, S1-08 отвечает за сквозную проверку, а не за все тесты в последний день.

Ориентир суммарной трудоёмкости: **14–21 человеко-день**. Резерв при изменениях контрактов WB, необходимости дополнительных повторных загрузок или расширении проверки качества: ещё 20–30%. Это не обещание двухнедельного календарного спринта; в исходном документе спринт означает релизный инкремент.

## 7. Проверки приёмки

| Проверка | Ожидаемый результат |

| Те же условия, кликов меньше 30 либо они неизвестны | № 3 не блокируется неиспользуемым полем |

| Число чуть выше порога, округляемое до него | Сравнение по неокруглённому decimal, без изменения результата отображением |

| Импорт исправил прошлые значения | Новый прогон, прежний журнал неизменен; проверочная таблица старого run совпадает с его карточкой |

| Два продавца/кабинета с одинаковыми артикулами и именами | Нет смешения данных, норм и результатов |
| Новый кластер с похожим именем | Нет автоматического переноса старой истории |
| Достаточно пригодных данных, правила не сработали | «По проверенным правилам отклонений не найдено», не «данных мало» |
