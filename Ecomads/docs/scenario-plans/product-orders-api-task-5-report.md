# Заказы по товарам и общий ДРР: реализация API

20.10.2026. Реализовано в `main`, без коммита. По последующему запросу пользователя выполнен деплой; проверка ниже. Согласован первый этап: последние 30 закрытых дней по МСК; новый процесс не ставит годовую товарную догрузку.

## Что изменилось

- Добавлены `wb_product_order_days` (полный опубликованный снимок дня) и `wb_product_daily_orders` (кабинет, дата, артикул WB, сумма и количество заказов). Миграция `20261019231219_AddWbProductOrders` только добавляет таблицы и служебные поля, прежнюю статистику не преобразует.
- При завершении товарной воронки сохраняется разбивка по товарам. Сгруппированная воронка остаётся источником итогов кабинета и не выдаётся за товарную статистику.
- Новый worker раз в минуту восстанавливает не более пяти подходящих сохранённых ответов на кабинет. Запросы к WB для этого не нужны. Он не переигрывает состояния старых заданий и не переписывает существующие итоги кабинета.
- После обработки сохранённых ответов планируются только пробелы в 30 днях и обновление последних семи закрытых дней в текущем слоте автообновления. Свежие дни идут первыми, два соседних дня обрабатываются одним запросом при одной странице. Регулярная работа учитывает флаг автообновления.
- «Загрузить всё из WB» создаёт отдельный сохраняемый ручной запрос даже при выключенном автообновлении. Повторные нажатия объединяются; восстановление ответов предшествует новым запросам. Пауза существующего товарного задания не снимается автоматически.

## Контракт API и расчёт

Расширен существующий `GET /api/statistics/nomenclatures/{campaignId}?startDate=…&endDate=…`; массив и прежние рекламные поля сохранены.

| Новое поле | Смысл |
| --- | --- |
| `totalOrderSum: number / null` | Все заказы товара в ₽ за весь выбранный период; null, если нет подтверждённых строк товара за каждый день |
| `totalAdvertisingSpend: number / null` | Расход товара во всех кампаниях того же кабинета за весь выбранный период |
| `totalDrr: number / null` | `totalAdvertisingSpend / totalOrderSum × 100`, округление до двух знаков; null при отсутствии покрытия или нулевом знаменателе |
| `totalOrderDays`, `totalAdvertisingDays`, `totalExpectedDays` | Покрытие источников выбранного периода |
| `totalStatus` | `complete`, `preliminary`, `unavailable`; нулевой знаменатель объясняется отдельно и не превращается в ДРР 0% |
| `totalReason` | Способ расчёта, покрытие и причина недоступности |

Рекламное покрытие проверяется по всем известным подходящим кампаниям кабинета, включая архивные. Учитываются даты создания/завершения и фактически имеющаяся статистика. Дни кампаний должны иметь подтверждённые проверки и качество; сумма товарных расходов должна совпадать с расходом дня кампании. Неполная детализация и последнее наблюдение `no_data` не разрешают считать общий расход полным. Данные другого кабинета/владельца исключены. Расход открытой кампании не подменяет общий расход товара.

Отсутствующий товар не получает автоматически нулевые заказы. Существующий ноль сохраняется нулём. Частичный период не экстраполируется. Без явно заданных начала и конца новые показатели недоступны; перевёрнутый диапазон или диапазон свыше 366 дней возвращает 400. GET читает только БД и не запускает WB-загрузки. Данные старше 30 дней могут оставаться в хранилище, но новый процесс не догружает их.

Фронтенд подключён к обоим столбцам, сортировке до пагинации, мобильным карточкам и сведениям по товару. Старый ответ API без новых полей совместим: новые показатели становятся недоступными, без нулей и без общей плашки предупреждения.

## Защита импорта и очереди

- Публикация происходит в транзакции под блокировкой импорта кабинета после проверки всей цепочки: SHA256, кабинет, вид задания, выбранные даты, параметры запроса, пустые фильтры, последовательность offsets и ссылок страниц, уникальность артикулов, обязательные показатели и RUB при переданной валюте. Суммы должны помещаться в точность `numeric(18,2)`.
- Терминальная страница должна содержать менее 1000 товаров. Предыдущие страницы должны содержать ровно 1000. Пустой полный ответ считается отсутствием подтверждения, а не нулевым каталогом.
- Повторная обработка идемпотентна. Новый полный снимок заменяет весь день; старый не возвращает удалённые строки и не перезаписывает более новые показатели. Ошибочный/пустой новый ответ сохраняет прежние строки для диагностики, но снимает подтверждение актуального показателя.
- Источник `product_orders` использует существующий общий слот `funnel_products`, включая `operations_demand`, с текущим интервалом 30 минут. Лимит не увеличивался. Один шаг worker выполняет один HTTP-запрос/страницу; timeout остаётся две минуты. Между шагами доступны другие задания.
- Одновременно разрешено одно активное товарное задание кабинета. Уже заполненные даты пропускаются перед запросом. Данные текущей рекламы/расходов/группированной воронки имеют более высокий приоритет; годовая история заказов уступает товарной загрузке.
- `429` учитывает `Retry-After` и общий слот метода. После 24 часов без продвижения товарное задание ставится на паузу с `no_progress`. Продолжение сбрасывает отсчёт; пауза и продолжение доступны в кабинете.
- Ошибки доступа/формата/транспорта не порождают новые задания каждую минуту: последнее неудачное товарное задание требует явного повтора или ручного обновления. Для 401 сохраняется существующая блокировка подключения. Ошибки доступа 403/402 допускают явный повтор товарной загрузки после исправления доступа.
- Опубликованные дни удерживают исходный снимок и цепочку страниц от очистки журнала. Неприменимые старые снимки не удерживают очередь восстановления в пределах 30 дней.

Существующие годовые задания и общая политика старых источников не переделывались; новая защита отсутствия прогресса относится к товарным заданиям.

## Проверки

- Миграция применена на изолированном PostgreSQL; EF подтвердил отсутствие несохранённых изменений модели.
- Целевые прогоны успешны: 15 тестов импорта/кластеров; затем 14 тестов товаров, HTTP-сценария и актуального API решений; после добавления ручного обновления — 28 тестов товаров и планировщика, без ошибок и пропусков.
- Полный прогон на отдельном PostgreSQL: 250 из 251 успешны. Единственный оставшийся E2E-сценарий содержал старое количество источников и обращение к ранее удалённому legacy API решений. Он актуализирован: проверяет новый источник, реальный API товаров, nullable и изоляцию владельцев; повторный прогон успешен. Действующие решения рекомендаций дополнительно проверены их отдельными HTTP-тестами. Первый общий прогон на стандартном контейнере упёрся в лимит соединений; изолированный прогон выполнялся без пула соединений.
- TypeScript, 16 frontend-тестов и Vite build успешны. Визуально проверены известная сумма, известный ноль, прочерк, общий ДРР, сортировка и мобильная карточка. [Desktop](product-orders-evidence/desktop-orders.png), [mobile](product-orders-evidence/mobile-orders.png). Скриншоты используют тестовые значения, не production-данные.
- На production только чтением проверены структура, параметры запросов и контрольные суммы 28 сохранённых товарных ответов: 28 совместимы, 0 несовместимы. Новых WB-запросов и записей в production не выполнялось.

### Дальнейшая эксплуатация

Обычный деплой создаёт резервную копию БД и применяет аддитивную миграцию. После старта сначала выполняется локальное восстановление; затем — дозагрузка пробелов. Проверить число опубликованных дней, `ProductOrdersError`, источник `product_orders` в журнале, продвижение offsets и общий ДРР на периоде с полным рекламным покрытием. Некоторые ДРР могут остаться недоступными при неполной рекламной истории — это ожидаемая защита, а не повод подставлять расход одной кампании.

При необходимости товарное задание можно приостановить отдельно. Для отката приложения новые таблицы сохраняются; удалять их и выполнять `Down` в production не требуется.
