## Этап 0 — обязательная проверка интеграции

Статус: рекламное ядро, воронка и отчёт Джема по поисковым запросам подтверждены реальными ответами; сверка Excel и отдельный метод для минус-фраз остаются открытыми. Отсутствие кластерной выручки подтверждено как ограничение текущего доступного источника.

Входы: базовый WB-токен только для чтения, кампании для проверки, по возможности Excel WB и Evirma за общий период. Секреты не помещать в документ, Git, логи или текст отчёта.

1. Проверить категории и режим токена, доступ без X-Client-Secret, способ подтверждения идентификатора продавца. Проверить seller-info и promotion/count по необходимости, не расходуя квоту бессистемно.
2. Проверить `/api/advert/v2/adverts`, `/adv/v3/fullstats`, `/adv/v1/normquery/stats`, `/adv/v0/normquery/get-minus`. Установить версии контрактов, ограничения пачек, типы кампаний, реальные интервалы и глубину истории.
3. Сравнить WB API и Excel на одинаковых кампаниях/датах: расход, заказы, сумма заказов, отмены и фильтр «Прямая». Явно описать расхождения, не объявлять показатели эквивалентными без проверки.
4. Проверить кластерную выручку, CPM/CPC и связь с артикулами. Evirma использовать для контрольного сравнения при наличии выгрузки, а не как обязательный производственный источник.
5. Проверены sales-funnel и положительный сценарий search-report на текущем токене: отчёт Джема возвращает данные. Для кабинета без Джема позже отдельно проверить отказ доступа. Ошибку доступа не приравнивать автоматически к отсутствию подписки; различать отсутствие прав, временный сбой и подтверждённое ограничение.
6. Составить матрицу «функция → endpoint → поля/единицы/гранулярность → лимиты → свидетельство → решение». Обезличить сохранённые примеры; указать даты проверки и официальные источники.

Критерий завершения: рекламное ядро проверено на реальном кабинете, ограничения описаны и доведены до пользователя. При отсутствии токена допустимы подготовка тестового клиента, проверка документации и изолированные тесты; этап остаётся незавершённым, совместимость WB не заявляется.

### Экономное использование реального токена

Пользователь отдельно потребовал беречь квоту: возможен лимит порядка одного запроса в час. Это предположение, а не подтверждённый лимит всех методов.

- До первого запроса прочитать актуальную документацию по каждому нужному методу и типу токена; составить минимальную последовательность с учётом общих либо независимых квот. Не считать лимиты независимыми без проверки.
- Не использовать статистические методы для повторного ping или проверки авторизации. Не запускать несколько диагностических клиентов параллельно для одного кабинета.
- Уточнить, используется ли токен/кабинет другими интеграциями и были ли недавние запросы; неизвестную занятость квоты учитывать консервативно.
- По возможности получать одним разрешённым запросом полезную пачку кампаний и согласованный период для сверки, а не тратить квоту на одиночные пробы. Размеры и даты сначала проверить локально по контракту.
- Сохранять полезные ответы локально в исключённом из Git месте без заголовка авторизации; для тестовых fixtures обезличивать данные. Повторять отладку на сохранённых ответах.
- Логировать только безопасные сведения о методе, времени, статусе и заголовках лимита. Не выводить токен или полный запрос с секретами.
- После 429 соблюдать указанное WB время ожидания; сохранять следующую попытку, не делать немедленных повторов. Час ожидания использовать для независимой разработки.
- Не запускать бесконтрольные эксперименты на реальном API и не обходить квоту заменой токенов.

### Сбор и хранение

- Первичная загрузка — последние 30 завершённых дней в пределах доказанных ограничений API. Автоматическая догрузка до 90 дней позже. Не обещать недоступную историю.
- Для быстрой проверки по текущему кабинету по умолчанию выбирать активные и приостановленные кампании (34 из 210 на дату проверки, одна пачка fullstats). UI позволяет указать конкретные ID, включая завершённые; полный исторический сбор всех кампаний потребует нескольких запросов с часовым интервалом. Частичный выбор не годится для расчёта общего ДРР по всему кабинету.
- Отчётные даты по Москве; технические отметки времени UTC. Отображать завершённость и покрытие периода.
- Повторное нажатие возвращает существующее активное задание, а не создаёт дубль. Кнопка не обходит лимит; UI показывает ожидание и следующую попытку.
- Сохранять задания, прогресс и время следующей попытки в PostgreSQL; использовать существующий hosted-service подход без обязательного нового брокера.
- 401 останавливает сбор до восстановления доступа; 403 показывает проблему доступа; 429 учитывает заголовки и лимит; временные 5xx имеют ограниченные повторы. Ошибка одного метода не должна выдавать частичный сбор за полный.
- Повторно загруженные дни заменяют соответствующие API-данные, не суммируются с ними. Совместимость со старыми интервальными Excel-строками не поддерживается. Агрегация apps/nms не должна повторно прибавлять родительские итоги.
- Использовать decimal для денег; явно отделять неизвестное значение от нуля.

### Нормы и расчёты

- Нормы кабинета и переопределения кампании; пустое значение наследует кабинет. Цель и своё название кампании сохраняются отдельно от данных WB.
- Изменения применяются при следующем расчёте; сохранять версию норм, использованную в расчёте.
- Отклонения от среднего за семь завершённых предыдущих дней, временный порог 40%; недостаточное покрытие не выдавать за полноценное сравнение.
- Без выручки кластера не рассчитывать кластерный ДРР и прогнозы на его основе. Не присваивать эффективность по отсутствию сработавшего правила.
- Расход без заказов требует подтверждённых нулевых заказов, а не отсутствующего поля. Уже заминусованный кластер не рекомендовать минусовать повторно.
- В [официальном описании Promotion API](https://dev.wildberries.ru/en/docs/openapi/promotion?locale=ru%2F) есть `POST /adv/v0/normquery/get-minus`: запрос до 100 пар кампания/артикул возвращает активные минус-фразы. Метод пока **не проверен текущим токеном** и не подключён; до этого не выдавать автоматическое действие «добавить в минус-фразы».
- Правила остаются источником решений; LLM не восполняет пропуски данных выдуманными метриками.

- Данные: кластер у нескольких артикулов, артикул в нескольких кампаниях, отсутствие выручки/метрик CPC, нулевые знаменатели, неполные периоды, повторный импорт дня.
- Нормы: наследование, переопределение, версия расчёта, отсутствие ложной рекомендации из-за null.
- Telegram: срок и однократность кода, отписка, отсутствие вчерашних данных, ошибки доставки, повторное нажатие.
- Сквозной путь: подключить → загрузить → увидеть метрики → изменить нормы → пересчитать → отправить сводку.
- Выполнить подходящие backend-тесты и frontend build; отличать тесты на fixtures от подтверждения реальным WB API. Существующие integration-тесты используют PostgreSQL.

Сравнение за июль **не подтвердило эквивалентность** API и Excel: за 01–07.07 API-расход по кампании 35174765 равен 82 259,89 ₽, а в строках Excel с конверсией «Прямая» — 71 125,70 ₽; для 35736322 — 27 717,69 ₽ и 23 538,64 ₽. Пользователь предварительно уведомлён в чате об отключении кластерного ДРР и зависимых правил в API-версии.

**Формулировка продуктового ограничения:** кластерный ДРР по текущему доступному API и токену корректно рассчитать нельзя. [Документация метода кластеров](https://dev.wildberries.ru/openapi/promotion) и реальный ответ дают расход и заказы, но не выручку кластера; выручку кампании/товара нельзя обоснованно распределить между кластерами. Для демки исключить кластерный ДРР и только те правила, которым необходима эта метрика. Не утверждать, что любой API WB навсегда лишён такого источника: платный «Джем» не проверен, а данные по поисковым запросам могут отличаться по смыслу от кластеров.

### Воронка продаж, проверена 2026-09-30

Один запрос `POST /api/analytics/v3/sales-funnel/products` за 01–07.07.2026 с `nmIds` 24 артикулов двух кампаний вернул HTTP 200, `data.products` для всех 24. В `statistic.selected` есть `orderCount`, `orderSum`, `openCount`, `cartCount`, а период ответа совпал с запрошенным. Сумма `orderSum` по этим артикулам — 1 744 895 ₽, `orderCount` — 1707. Ответ сохранён локально в игнорируемом Git файле `.env.wb-funnel-response.json` без заголовка авторизации.

По [официальной документации WB](https://dev.wildberries.ru/openapi/analytics) базовый токен для этого метода ограничен двумя запросами в час с интервалом 30 минут; данные обновляются примерно раз в час. Воронка возвращает **все** заказы товара, включая нерекламные, поэтому её `orderSum` нельзя подставлять в рекламный ДРР или считать выручкой кластера.

Все 24 проверенных артикула состоят в нескольких рекламных кампаниях (максимум 26). Общий ДРР возможен на уровне товара/кабинета только после сбора расходов по **всем** его кампаниям за тот же период; числитель из двух тестовых кампаний был бы занижен. Статус: источник общего ДРР подтверждён, сама метрика в продукте не реализована и не проверена сквозным сценарием. Пользователь уведомлён в чате о результате и условии полноты.

Точную таблицу каждого метода нужно ещё зафиксировать из первоисточника; поисковая копия стороннего SDK не является достаточным основанием для продакшен-расписания.
