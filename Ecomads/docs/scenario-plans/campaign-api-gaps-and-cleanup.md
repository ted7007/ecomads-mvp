### Как считается рекламная позиция

Выбираются положительные дневные позиции за явно заданный период, затем считается среднее арифметическое известных дневных значений. Весов исходных наблюдений в БД нет: показатель не объявляется взвешенной позицией WB за весь период. Подсказка раскрывает способ и количество дней. Null, нулевые и отрицательные позиции не превращаются в нули. При неполном источнике, отсутствии позиции у части строк или незавершённом текущем дне статус предварительный. Дни без строки кластера не трактуются как нулевая позиция.

Проверка production выполнена только на чтение: 35 404 строки кластеров, положительная позиция у 35 330. Это подтверждает наличие источника, но не гарантирует данные для любого выбранного периода/кластера.

## Следующая задача: все заказы и общий ДРР товара

### API-01. Сохранить данные по товарам

**Факт:** `WbSalesFunnelImporter.ReadProductsPage` читает `nmId` и показатели выбранного/прошлого периода, но состояние страницы сохраняет агрегат и множество идентификаторов. `ImportProductsAsync` пишет общий итог кабинета. Ветка истории также сохраняет итог по кабинету. Восстановить товарные значения из этих итогов нельзя.

**План:**

1. Добавить сущность и миграцию `WbArticleDailyOrders` с ключом кабинет + `nmId` + дата, суммой/количеством заказов, временем загрузки и связью с принятым снимком/качеством источника. Товар не смешивать с внутренним ID кампании.
2. До изменения ветки истории проверить её фактический ответ и место идентификатора товара. Описать отдельные преобразования для текущего и исторического источника, выбранного и прошлого периодов.
3. В пагинации сохранять товарные показатели в staging или состоянии снимка, а не только агрегаты. Публиковать данные после полного подтверждённого набора страниц атомарно с существующим итогом кабинета; сбой страницы не должен выдавать частичный набор за полный.
4. Сохранить проверку качества, идемпотентность, повторную загрузку и бюджет очереди. Отсутствие записи не равно нулю; известный ноль допускается только при подтверждённом покрытии соответствующего источника.

### API-02. Вернуть значения для выбранного периода

**Факт:** `StatisticsController.GetNomenclatures` использует `CampaignNomenclatureStatistics` одной кампании; `Revenue` в ней — рекламные заказы.

**План:**

1. Для товара текущей кампании собрать все заказы из нового источника в границах того же кабинета, владельца и выбранного периода.
2. Для общего ДРР собрать рекламный расход того же товара **по всем кампаниям этого кабинета**, включая архивные, за тот же подтверждённый набор дат. Формула: общий рекламный расход товара / все заказы товара в ₽ × 100.
3. Добавить nullable `totalOrderSum`, `totalAdvertisingSpend`, `totalDrr`, статус, причину и счётчики покрытия. До реализации согласовать и зафиксировать точный JSON-контракт в этом документе. При неполном покрытии не объявлять показатель полным; при неизвестных данных или нулевом знаменателе ДРР — null.
4. Не вычислять числитель только из расхода открытой кампании. Не использовать итог заказов всего кабинета как знаменатель товара. Не менять смысл существующих рекламных полей.
5. Подключить оба столбца к новым полям и сортировке по всему набору до пагинации. Неизвестные значения — последние в обоих направлениях; причина в подсказке без общей плашки предупреждения.

### API-03. Заполнить историю и проверить

**Факт:** существующие дневные итоги кабинетов не содержат товарную разбивку.

**План:** проверить наличие полных сохранённых исходных снимков и возможность контролируемого переигрывания. Использовать только проверенные полные цепочки с метаданными принятия; не разбирать raw JSON при каждом запросе страницы. При отсутствии подходящих снимков загрузить историю обычной очередью в рамках лимитов WB. Не обещать восстановление периода, которого источник уже не предоставляет.

**Приёмка:** интеграционные тесты на два кабинета/владельца, один товар в двух кампаниях, архивную кампанию, другой товар, даты вне диапазона, известный ноль, неизвестное значение, нулевой знаменатель, неполную пагинацию, повтор загрузки и пересекающиеся снимки. Суммы по товару должны сверяться с исходным снимком, числитель — с рекламной статистикой всех кампаний. До backfill старые периоды честно остаются недоступными.
