# Какие данные WB попадают в EcomAds

Подробная цепочка **семи строк экрана загрузок** с реальными JSON проверочных запросов: [wb-seven-loads-dependency-chain.md](wb-seven-loads-dependency-chain.md).

Снимок подключения `218f4679-4dc1-4543-b0e7-426e6f11d080` («Кабинет WB») на 3 октября 2026 года, 15:54 Владивосток / 08:54 МСК. В базе есть второе подключение с тем же названием, поэтому цифры ниже относятся **только к этому ID**. Это фактура по коду приложения, сохранённым данным и журналу заданий. **Сырые успешные тела ответов WB приложение не хранит.** Поэтому примеры ниже показывают читаемые поля ожидаемой структуры, а не дословные ответы на прошлые запросы. Исключение: в журнале зафиксирован фактический ответ `HTTP 200` с телом `null` у `fullstats`.

## Что сейчас есть в кабинете

| Источник в БД | Объём и период | Значение |
| --- | --- | --- |
| Кампании | 212 | Метаданные списка кампаний WB. |
| Дневная реклама | 306 строк, 01.07–01.10 | Строки по отдельным кампаниям и датам; это не 306 полностью подтверждённых дней кабинета. |
| Проверки расхода | 306 записей, 01.07–01.10 | Подтверждают только конкретные кампании и дни. |
| Поисковые кластеры | 353 строки, 21.09–01.10 | Расход и действия по сочетанию кампании, товара, текста и дня. |
| Джем | 374 строки, 02.07–01.10 | Запросы в сохранённых отчётах за разные интервалы; пересекающиеся отчёты нельзя складывать. Есть 30 записей проверки товаров за 25.09–01.10. |
| Все заказы кабинета | 30 дневных строк, 02.09–01.10 | Сумма и количество заказов из воронки, включая нерекламные. |

Пример сохранённых значений: кампания WB `35174765` («Бумажные салфетки Поиск») за **01.10** имеет расход **0,26 ₽**, **1 показ**, **0 кликов**, рекламную сумму заказов **0 ₽**. Все заказы **всего кабинета** за тот же день — **61 660 ₽, 39 заказов**. Эти значения происходят из разных методов WB и относятся к разным уровням: кампания и весь кабинет.

После исправления обработки `null` 3 октября задание текущей рекламы завершило повторную пачку, но **24 кампании WB снова не подтвердил**. Архив к моменту снимка обработал первую пачку из 50 кампаний без строк данных и ждёт следующего слота `fullstats`. Сохранённые ранее рекламные строки остались на месте.

## Запросы к WB, структура JSON и назначение

Схемы сокращены до полей, которые действительно читает текущий импортёр. `…` означает другие поля ответа WB. Параметры и лимиты ниже — те, которые **отправляет и применяет EcomAds**; они не являются копией полного актуального тарифа WB.

| Метод WB | Что отправляем | Какие поля читаем из ответа | Куда попадает |
| --- | --- | --- | --- |
| `GET /api/advert/v2/adverts` | Токен рекламы, без списка ID | `adverts[].id`, `status`, `settings.name`, `settings.payment_type`, `nm_settings[].nm_id`, `timestamps.created/started/deleted/updated` | Список кампаний, статус и даты жизни, связь с товарами, планирование архива и полноты. |
| `GET /adv/v3/fullstats` | До 50 ID, `beginDate`, `endDate`, максимум 31 день | Массив `advertId`, `days[].date/sum/sum_price/views/clicks/atbs/orders/canceled`, `apps[].nms[]` с такими же метриками товара | Расход, рекламная сумма заказов, показы, клики, CTR, рекламный ДРР, дневной график, товары кампании. Текущие и архивные задания делят слот метода. |
| `POST /adv/v1/normquery/stats` | `from`, `to`, до 100 пар `{advertId,nmId}`, максимум 7 дней | `items[].advertId/nmId/dailyStats[].date/stat.normQuery/spend/views/clicks/atbs/orders/shks/avgPos/cpc/cpm/ctr` | Таблица поисковых кластеров и рекомендации по кластерам. WB не даёт выручку кластера. |
| `POST /api/v2/search-report/product/search-texts` | `currentPeriod`, до 50 `nmIds`, максимум 7 дней, топ 30 текстов | `data.items[].nmId/text/frequency.current/weekFrequency/avgPosition.current/medianPosition.current/openCard.current/addToCart.current/orders.current` | Отдельный сохранённый отчёт Джема и, при совпадении периода и текста, фиолетовые колонки таблицы кластеров. |
| `POST /api/analytics/v3/sales-funnel/grouped/history` | `selectedPeriod`, `aggregationLevel: "day"`, весь кабинет, максимум последние 7 дней | `data[].currency/history[].date/orderCount/orderSum/openCount/cartCount/buyoutCount/buyoutSum` | Свежие дневные суммы всех заказов кабинета, карточка «Заказы», график заказов и знаменатель общего ДРР. |
| `POST /api/analytics/v3/sales-funnel/products` | Два соседних однодневных периода, `limit: 1000`, `offset` для страниц | `data.products[].statistic.selected/past.orderCount/orderSum` | Дозагрузка старых дневных сумм всех заказов; промежуточные суммы и номер страницы сохраняются в задании. |

Упрощённая иллюстрация формы `fullstats`:

```json
[{"advertId":35174765,"days":[{"date":"2026-10-01T00:00:00Z","sum":0.26,"sum_price":0,"views":1,"clicks":0,"atbs":0,"orders":0,"canceled":0,"apps":[{"nms":[{"nmId":123,"sum":0.26,"sum_price":0,"views":1,"clicks":0,"atbs":0,"orders":0,"canceled":0}]}]}]}]
```

Здесь **числа верхнего уровня соответствуют сохранённой дневной строке**, но вложенный `nmId` и его показатели показаны только для формы: сырой JSON конкретного ответа не сохранён. Фактически наблюдавшийся при повторной загрузке другой ответ был целиком:

```json
null
```

Он не означает нулевой расход. EcomAds оставляет все ID такой пачки непроверенными и делает одну дополнительную проверку, затем продолжает очередь с предупреждением о неполноте.

Упрощённые формы остальных ответов: `{"adverts":[{"id":…, "status":9, "settings":{"name":"…"}, "nm_settings":[{"nm_id":…}]}]}`, `{"items":[{"advertId":…, "nmId":…, "dailyStats":[{"date":"…", "stat":{"normQuery":"…", "spend":…}}]}]}`, `{"data":{"items":[{"nmId":…, "text":"…", "frequency":{"current":…}, "avgPosition":{"current":…}}]}}`, `{"data":[{"currency":"RUB", "history":[{"date":"…", "orderSum":…, "orderCount":…}]}]}`, `{"data":{"products":[{"statistic":{"selected":{"orderSum":…, "orderCount":…}, "past":{"orderSum":…, "orderCount":…}}}]}}`. Это схемы по импортёрам, не снятые тела сетевых ответов.

## Что зависит от какого источника

| Элемент сайта | Источник и расчёт |
| --- | --- |
| Сводка: линии «Расход», «Заказы с рекламы», «CTR», клики, CPC | `fullstats` → `campaign_statistics` → `/api/statistics/daily`. CTR = клики / показы × 100; CPC = расход / клики. |
| Сводка: линия «Заказы» и карточка «Заказы» | `grouped/history` и `products` → `wb_store_daily_orders` → `/api/statistics/daily`. Линия показывает **сумму заказов в рублях**, хотя подписана «Заказы». |
| Сводка: линия и карточка «ДРР от заказов» | Подтверждённый рекламный расход `fullstats` + все заказы из воронки **за одинаковые дни** → серверный `/api/statistics/coverage`. При неполноте график оставляет разрывы, карточка может показать предварительный ДРР по подтверждённым дням. |
| Сводка: таблица кампаний, рекламные KPI и рекомендации | `fullstats` → `/api/projects`; нормы берутся из настроек EcomAds. Неполные дни ограничивают сравнения и вывод рекомендаций. |
| Страница кампании: дневной график, расход, рекламные заказы, рекламный ДРР, CTR, CPC | `fullstats` → `/api/statistics/daily?campaignId=…`, `/api/projects`, `/api/statistics/nomenclatures/{id}`. Рекламный ДРР = расход / рекламная сумма заказов × 100. |
| Страница кампании: сравнение расхода со средней прошлой неделей | `fullstats` → `/api/wb/campaigns/{id}/spend-trend`; сейчас выводится текст под графиком, а не отдельная линия. |
| Страница кампании: таблица кластеров и рекомендации | `normquery/stats` → `/api/wb/campaigns/{id}/clusters`. |
| Страница кампании: Джем | `search-texts` → `/api/wb/campaigns/{id}/jam`; выбранный сохранённый недельный отчёт независим от общего фильтра 7/14/30 дней. |
| Блоки свежести на сводке и кампании | Сохранённые проверки, строки и задания → `/api/wb/data-state`; показывают период, полноту, время проверки и состояние очереди. |

Выбор карточек над дневным графиком включает соответствующие линии. Пунктир предыдущего периода появляется, когда в обеих сериях есть значения за каждый день и выполнена проверка количества загруженных кампаний (для заказов — только наличия дневных сумм). Это более простая проверка, чем серверная оценка полноты общего ДРР. Разрыв линии обозначает отсутствие загруженного значения, не ноль.

## Ограничения точности этой фактуры

1. Сырые успешные тела WB и заголовки каждого прошлого ответа не архивируются. Сохранённые строки позволяют показать использованные значения, но не восстановить ответ байт в байт или неизвестные поля WB.
2. `HTTP 200 null` у `fullstats` подтверждён журналом приложения. Почему WB выбрал именно такой ответ для этих ID, из одного `null` определить нельзя. Считать его пустым массивом с нулевым расходом было бы ошибкой.
3. Новые диагностические запросы к WB расходуют его методные слоты и могли бы задержать текущую очередь; для этого снимка они не отправлялись.
4. Числа в таблице кабинета — снимок на указанное время; архив и дозагрузка продолжат менять их.

Отдельная находка для проверки лимитов: текущий код ставит для `fullstats` **1 час** между запросами и для списка кампаний тоже **1 час**. Доступная при подготовке этой заметки [публичная спецификация рекламы WB](https://dev.wildberries.ru/docs/openapi/promotion) указывает для `fullstats` **3 запроса в минуту с интервалом 20 секунд**, а для `/api/advert/v2/adverts` — **5 запросов в секунду**. [Спецификация аналитики](https://dev.wildberries.ru/docs/openapi/analytics) указывает для `grouped/history` и Джема `search-texts` **3 запроса в минуту**. Это расхождение с локальной конфигурацией, а не доказательство фактического лимита именно подключённого токена: перед изменением очереди нужно сверить актуальную документацию и ответы `429` / `Retry-After` этого кабинета. Диагностические запросы ради проверки лимита здесь не отправлялись.
