# Задача на неделю: запустить и довести Telegram-бота EcomAds

**Исполнитель:** второй разработчик с AI-помощником. **Оценка:** 4 рабочих дня + 1 день на исправления и приёмку. **Приоритет:** основной объём недели вместо общего бэклога техдолга. Дата постановки: 6 октября 2026.

## Зачем

Telegram-интеграция написана, но владелец ещё не проверял реальный сценарий. Нужно создать бота, подключить его, пройти путь пользователя целиком, исправить найденные проблемы и получить удобную сводку в настоящем Telegram. Отдельно предложить развитие функции. Наличие кода и мок-тестов не считать доказательством работающей интеграции.

**Готовый результат:** пользователь привязывает личный чат, выбирает кабинет WB, нажимает «Отправить вчерашнюю сводку» и получает понятное сообщение по шаблону. Ошибки видны в интерфейсе, отключение работает, повторное нажатие не даёт скрытых дублей. Исполнитель демонстрирует сценарий и передаёт бота, настройки, исправления и краткий план развития.

## Исходное состояние

- `Services/Telegram/TelegramBotClient.cs`: клиент getUpdates/sendMessage.
- `Services/Telegram/TelegramUpdatesWorker.cs`: long polling, привязка по одноразовой ссылке, команды `/start`, `/help`, `/stop`; обрабатываются только личные чаты.
- `Controllers/TelegramController.cs`: создание ссылки, список/отключение чатов, ручная сводка за вчера по МСК, проверки полноты данных и журнал доставок.
- `Data/Models/TelegramModels.cs`: привязки, коды, offset и статусы доставки.
- `ClientApp/src/pages/WbStoresPage/`: интерфейс подключения и отправки.
- `Ecomads.WebApplication.Tests/Integration/TelegramSummaryTests.cs`: тест полноты данных и повторной отправки. Его недостаточно для проверки живого бота.
- В `ops/compose.production.yml` уже предусмотрены `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME`, передаваемые в `Telegram:BotToken`/`Telegram:BotUsername`.

Первые пять путей — внутри `Ecomads.WebApplication/`. Реальное состояние бота и конфигурация серверов на момент постановки не проверены.

## 1. Создать и подключить бота — примерно 4 часа

1. Создать бота через BotFather: имя, username, короткое описание и команды start/help/stop. Зафиксировать владельца и способ передачи управления; рабочий бот должен оставаться под контролем владельца продукта. Если создание требует его Telegram-аккаунта, подготовить действия для совместного выполнения, параллельно продолжать локальные проверки.
2. Для отладки использовать отдельного тестового бота и личные тестовые чаты. Не подключать один токен одновременно к локальному и рабочему polling-процессу.
3. Подключить токен через секреты окружения. Не помещать его в Git, скриншоты, задачи, промпты AI и логи. Проверить, что ошибки HTTP не раскрывают URL с токеном.
4. Проверить идентичность бота, получение команд и отправку ответа. Для текущего long polling проверить отсутствие webhook; не переключать способ доставки без необходимости.
5. Записать короткую инструкцию запуска, перезапуска и замены токена. Запуск в рабочем окружении выполняется в согласованное окно; не считать его сделанным по одному успешному локальному тесту.

Создание через `/newbot` описано в [официальном руководстве Telegram](https://core.telegram.org/bots/tutorial). Ограничение совместимости webhook и long polling — в [Telegram FAQ](https://core.telegram.org/bots/faq).

## 2. Пройти пользовательский путь и исправить ошибки — примерно 10 часов

Пройти реальным пользователем: приложение → ссылка → бот → подтверждение привязки → приложение → выбор магазина → сводка → отключение. Вести короткий журнал: сценарий, ожидаемое поведение, фактическое поведение, исправление, повторная проверка.

Уже видимые по коду места для проверки:

- Ошибки Telegram записываются в общий `error`, который отображается внутри скрываемой формы WB. Показывать их рядом с Telegram-действием.
- Кнопка сводки использует `stores.data[0]`. Дать выбрать магазин и явно показать, по какому кабинету отправляется сообщение.
- После привязки предлагается перезагрузить страницу. Добавить проверку привязки по кнопке или при возврате в приложение.
- UI отображает `sent` и `failed`, но не `skipped`. Повторная отправка должна объяснять «Сводка уже отправлена», а не показывать непонятные нули.
- Любая существующая запись доставки сейчас блокирует повторную попытку, включая `failed` и `unknown`. Разобрать поведение каждого статуса: `sent` пропускать; для подтверждённого отказа предусмотреть безопасный повтор; при неизвестном исходе не повторять автоматически с риском дубля. Проверить также зависший `pending` и параллельные клики. Не обещать exactly-once доставку при сетевом тайм-ауте.

### Обязательная матрица проверки

| Сценарий | Ожидаемое поведение |
|---|---|
| Бот настроен / токен отсутствует / токен неверный | Рабочий сценарий либо понятная ошибка, без ложного «всё подключено» |
| `/start`, `/help` без персональной ссылки | Понятная инструкция, как связать аккаунт |
| Валидная / истёкшая / уже использованная ссылка | Привязка один раз либо объяснение, как получить новую |
| Два аккаунта приложения | Сводка идёт только в чат текущей привязки; перепривязка не оставляет доставку предыдущему владельцу |
| Один и два магазина | Отправляется выбранный кабинет, название и дата совпадают |
| Полные данные / неполные данные / нет кампаний | Сводка либо точное объяснение причины отказа; отсутствие данных не заменяется нулями |
| Два клика, повторный запрос, перезапуск приложения | Нет обычных повторных доставок и повторной обработки старых команд |
| `/stop` и отключение в приложении | Дальнейшая сводка в отключённый чат не уходит |
| Блокировка бота пользователем, временная ошибка, тайм-аут | Ошибка отражена корректно; нет бесконечных повторов или остановки всего worker |
| Несколько привязанных тестовых чатов, один недоступен | По каждому понятен исход; исправный получатель не теряется из-за чужой ошибки |
| Длинные названия, спецсимволы, нулевая выручка | Сообщение читаемо, отправляется, неопределённый ДРР обозначен «—» |

Основной путь, `/stop`, повторную отправку и блокировку проверить в настоящем Telegram. Редкие сетевые сбои, 429, конкурентные запросы и граничные данные воспроизвести управляемыми тестами. Не создавать нагрузку на настоящий Telegram для получения rate limit.

## 3. Привести сводку к шаблону — примерно 8 часов

Отдельный шаблон владелец пока не передавал. Ниже предложен рабочий вариант для первого прогона; если появится его образец, использовать его. Не добавлять LLM и генерацию советов.

```text
EcomAds · {название кабинета}
Рекламная сводка за {дата}, МСК

Расход на рекламу: {расход} ₽
Заказы из рекламы: {заказы}
Рекламная выручка: {выручка} ₽
Рекламный ДРР: {ДРР либо «—»}

Кампании по расходу — топ {N}
1. {название}: {расход} ₽ · {заказы} заказов · ДРР {значение}
2. ...

Данные: {время обновления с часовым поясом}
Открыть сводку за этот день: {ссылка}
Отключить сообщения: /stop
```

- Использовать уже вычисляемые показатели и текущий набор кампаний. Не называть рекламный ДРР общим ДРР магазина, не смешивать рекламные заказы со всеми заказами WB.
- Сохранить существующие условия полноты данных и формулы. Если метрика вызывает вопрос — зафиксировать его владельцу, а не «исправлять» расчёт самостоятельно.
- В базовом шаблоне только факты. Блоки «Требуют внимания», советы, сравнение с целями и рекомендации в новую сводку не включать. Это изменение представления сообщения, не изменение норм или рекомендательного движка.
- Выделить форматирование в отдельный небольшой formatter с тестами. Добавить читабельное форматирование денег, процентов, длинных названий и пустых значений.
- Сохранить компактность: до 10 кампаний, при переполнении сокращать список и названия, сохраняя итоговые метрики и ссылку. Не вводить многочастную доставку без необходимости.
- Соблюдать ограничение `sendMessage` 4096 символов после разбора entities; проверить длинный пример и выбранное экранирование по [Bot API](https://core.telegram.org/bots/api#sendmessage).
- Ссылка ведёт на сводку за указанный день; проверить поведение после входа, если пользователь не авторизован. Корректность домена проверить за reverse proxy.
- Показать владельцу реальные сообщения на телефоне: обычный кабинет, длинные названия и нулевая выручка. Дата периода — МСК, часовой пояс времени обновления подписан явно.

## 4. Предложить развитие функции — примерно 3 часа

Подготовить записку на одну страницу: какие проблемы пользователей решает Telegram, что показала проверка, какие 3–5 улучшений делать дальше. Для каждого — польза, оценка сложности, зависимость от данных/инфраструктуры и критерий успеха. В эту неделю реализовывать их не требуется.

Кандидаты для оценки, не утверждённый roadmap:

1. Утренняя доставка по расписанию: время пользователя, готовность данных, сообщение о задержке, защита от дублей.
2. Выбор кабинетов и частоты сообщений, пауза подписки.
3. Настройка состава сводки и компактного/подробного вида.
4. Кнопки «Открыть кабинет» и «Получить сводку» непосредственно в боте с проверкой доступа.
5. История доставки и понятный повтор после подтверждённой ошибки.

Предложить первым следующий небольшой релиз и объяснить выбор. Метрики на будущее: завершённые привязки, успешные доставки среди допустимых попыток, повторы/ошибки, отключения, переходы в продукт. Не обещать измерять прочтение сообщения обычным Bot API. Не внедрять новую аналитику в рамках этого задания.

## 5. Сдача и резерв — примерно 15 часов

Оставшееся время недели: регрессионные тесты, устранение обнаруженных проблем, ревью, показ владельцу и передача. Если дефекты займут резерв, сократить будущий roadmap до трёх пунктов; не сокращать проверку реального пути и отключения.

Передать:

- username и ссылку на бота, информацию о владельце, окружении и месте безопасного хранения токена — без самого токена;
- PR с исправлениями и тестами;
- протокол матрицы: что проверено вживую, что на моках, что осталось непроверенным;
- 2–3 скриншота реальных сообщений без секретов и чужих данных;
- инструкцию настройки, перезапуска, диагностики и отключения;
- краткий план развития с рекомендуемым следующим шагом.

**Критерий завершения:** владелец по инструкции привязывает свой тестовый чат и получает сводку выбранного кабинета по шаблону; повторная отправка объяснена; отключение прекращает доставку; критичные дефекты проверки устранены. Если использовались синтетические данные, это явно указано; отдельный итоговый прогон на доступном реальном кабинете зафиксирован либо честно отмечен как оставшаяся зависимость.

## Границы и работа с AI

Рекомендации владелец делает самостоятельно. Не менять их движок, UI, решения, нормы CTR/ДРР, формулы KPI, импорт WB и критерии готовности данных. Разрешено менять TelegramController только в части доставки, обработки ошибок и форматирования; выделять formatter в `Services/Telegram/`; править worker/client, локальный Telegram-интерфейс и соответствующие тесты. Узкие изменения модели доставки допустимы при доказанной необходимости, отдельной миграцией без переписывания существующих.

Вайб-кодинг использовать для formatter, тестовых сценариев, обработки UI-состояний и документации. Человек проверяет привязку аккаунтов, retry/deduplication, работу с секретами и реальные сообщения. Отдельная ветка и небольшие PR: подключение/диагностика → ошибки/доставка → шаблон/приёмка. Это постановка задачи для другого исполнителя: при подготовке документа бот не создавался, сообщения не отправлялись и код продукта не менялся.

### Стартовый промпт исполнителю

> Доведи Telegram-сценарий EcomAds по docs/refactoring-tasks/07-telegram-bot-end-to-end.md. Сначала изучи существующий код и подними отдельного тестового бота, затем проверь реальный путь привязка → выбор кабинета → сводка → отключение. Исправь ошибки и обработку статусов доставки, выдели formatter и внедри описанный фактический шаблон. Рекомендации, нормы, расчёты метрик и импорт WB не менять. Не передавай секреты модели и не записывай их в репозиторий. Сдай небольшие PR, результаты живых и автоматических проверок, скриншоты сводки, инструкцию владельцу и одну страницу предложений по развитию. Не заменяй живую проверку одними моками.
